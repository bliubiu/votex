### 1.2 分层健康度

| 维度 | 评级 | 说明 |
| :--- | :--- | :--- |
| **领域层纯度** | 优秀 | `votex-domain` 零 IO/零异步/零 ONNX/零反向依赖，依赖白名单严格 |

### 1.3 一句话结论

> 项目骨架（DDD 分层、仓储抽象、资源治理、事件总线）搭得**相当到位**，基础设施层甚至已经写好了 `EngineState`、`InferenceGate`、`ModelFileLocator` 等优质抽象。

## 二、P0 级致命问题（必须立即修复）

### P0-1 【致命】`application.yml` 全局失效，配置系统形同虚设

**证据链（已实测验证）**

1. `application.yml:81` 注释前缺少空格：
   ```yaml
   progressive_quality: true# 资源治理：防止长文本/批量推理占满系统资源触发 OOM 或 hang
   ```
   YAML 规范要求 `#` 前必须有空白才是注释，此行实际被解析为 **字符串** `"true# 资源治理：..."`。

2. 实测（临时探针 `crates/votex-infra/tests/zzz_yaml_probe.rs`，验证后已删除）：
   ```
   [Value 解析] Ok(String("true# 资源治理：…"))
   [AppConfig 解析] 失败: 解析 YAML 字符串失败: type mismatch: expected bool, found other
   ```
   `pipeline.progressive_quality` 声明为 `bool`（`crates/votex-domain/src/config/value_object.rs:426`），**整份配置反序列化失败**。

3. 失败被静默吞掉：
   - `crates/votex-cli/src/lib.rs:28-30`
     ```rust
     let app_config: Option<AppConfig> = std::fs::read_to_string(&config_path)
         .ok()
         .and_then(|c| serde_yml::from_str(&c).ok());   // ← 双重 .ok() 吞错
     ```
   - `crates/votex-gui/src/lib.rs:59-61` 同样写法。

4. **日志硬佐证**：`application.yml:76` 写的是 `execution_provider: cpu`，而 `logs/votex-20261003.log` 三条启动记录全部是：
   ```
   [2026-10-03 02:49:35.908] [INFO] [votex_cli:61] - ONNX Runtime 执行提供器: Auto
   ```
   `Auto` 正是 `lib.rs:54` 的硬编码回退值 —— 证明配置文件从未被读取成功。

**实际危害**

- 用户修改的 `tts.*` / `asr.*` / `translation.*` / `resource.*` / `output.*` **全部不生效**
- 最危险的一条：`inference.execution_provider: cpu` 不生效，程序回退 `auto`（优先 DirectML GPU）。而 `application.yml` 自己第 72-74 行的注释写着：
  > 「注意：DirectML 在部分显卡驱动上会导致进程崩溃（非可捕获错误），若无 GPU 加速需求请保持 cpu」
  即**本可避免的崩溃保护被静默绕过**
- `models.download.timeout: 300` 是配置项但**代码中无消费者**（见 P1-6），下载无超时保护

**修复建议**

1. `application.yml:81` 改为 `progressive_quality: true  # 资源治理：…`（`#` 前补空格）
2. 配置加载改为**显式失败**：解析失败时 `tracing::error!` 打出具体行号并明确提示，不允许 `.ok()` 静默降级
3. 增加启动自检测试：断言 `ConfigLoader::from_file(Path::new("application.yml"))` 必须成功
4. 给 `AppConfig` 所有字段加 `#[serde(default)]`，避免单个字段错误导致整份配置失效

### P0-4 【致命】模型下载零完整性校验 + 校验失败可被绕过

**位置**：`models/registry/*.yaml`（28 个清单 / 165 个文件条目）、`crates/votex-infra/src/download/downloader.rs:105-156`

**实测数据**

| 检查项 | 结果 |
| :--- | :--- |
| 含 `sha256` 字段的清单 | 1 / 28 |
| 有实际 sha256 **值**的文件条目 | **0 / 165**（唯一那个清单里 8 处全是 `sha256: ~`） |
| 含 `size` 字段的清单 | 1 / 28（3 个条目） |

**绕过路径**（`downloader.rs:135-138`）

```rust
Ok(true)  => 通过
Ok(false) => 删除文件、记录错误、换下一个源
Err(e)    => tracing::warn!("SHA256 校验出错: {}", e);   // ← 然后 fall through 到"下载成功"
```

校验过程本身出错（文件被锁、权限不足、IO 错误）时，控制流**继续往下走进"下载成功"分支**。
同理 `:79-84`，文件已存在且 `expected_size == None`（占绝大多数）时直接判定完成，**损坏文件永不被发现**。

**危害**：供应链攻击面。被投毒/截断的 ONNX 模型会被直接加载执行，而本 crate 存在 `unsafe` mmap（`tts/qwen3_tts.rs:221-224`）—— 恶意文件可导致任意内存访问。

**修复**：
1. 为 165 个条目补齐 sha256（HF / ModelScope LFS 元数据可取），CI 加 lint 强制
2. `Err(e)` 必须视为失败（`last_error = Some(e); continue;`）
3. 写入 `dest.part` 临时文件 → 校验通过 → `rename`
4. 断点续传校验 ETag / Last-Modified，不匹配则从 0 重下

### P0-5 【致命】数据库错误被系统性静默吞没

**位置**：`crates/votex-infra/src/persistence/*_repo.rs`（7 个仓储）

普遍模式：

```rust
let conn = match self.conn.lock() { Ok(c) => c, Err(_) => return Vec::new() };
let mut stmt = match conn.prepare(...) { Ok(s) => s, Err(_) => return Vec::new() };
rows.filter_map(|r| r.ok()).collect()     // 坏行静默丢弃
```

**最危险后果**：`find_by_id()` 用 `.ok()`（`asr_task_repo.rs:120`、`ocr_repo.rs:38`）—— 一次瞬时 IO 错误会让调用方认为"任务不存在"，从而**重复创建任务 / 重新下载 GB 级模型**。`find_incomplete()` 返回空 Vec 会让启动恢复逻辑静默跳过所有待办任务。

**并发问题**：`ocr_repo.rs:41-105` 的 `save()` 先写任务行、再在 `for` 循环里逐页 INSERT，**全程无事务**，中途崩溃产生半截任务。`:113-116` 的删除两条 DELETE 各自隐式提交，非原子。

**修复**：查询方法统一返回 `Result<Vec<T>, DomainError>`；`save`/`delete` 包进事务；错误至少 `tracing::error!` 后再降级。

### P0-6 【致命】SQLite 外键约束从未启用，级联删除完全失效

**位置**：`crates/votex-infra/src/persistence/db.rs:85`

```sql
task_id TEXT NOT NULL REFERENCES ocr_tasks(id) ON DELETE CASCADE
```

但**全 workspace 从未执行 `PRAGMA foreign_keys = ON`**（已确认零命中）。SQLite 默认关闭外键，这条 `ON DELETE CASCADE` **完全不生效**。

**附带**：唯一迁移机制是 `db.rs:151-154` 的 `let _ = conn.execute_batch("ALTER TABLE … ADD COLUMN …")`，无 `user_version` 版本表，错误被 `let _ =` 吞掉（包括 SQLITE_BUSY / 磁盘满这类真失败）。

**已核验正常**：WAL 已启用（`db.rs:43`）、`busy_timeout=5000`、**全部 SQL 参数化**（未发现任何 `format!` 拼接 SQL 的注入点）。

**修复**：`init_schema` 内逐连接执行 `PRAGMA foreign_keys = ON`；引入 `PRAGMA user_version` + 显式迁移列表。

### P0-7 【致命】事件总线持锁回调 → 自死锁 + 锁毒化

**位置**：`crates/votex-infra/src/event/mod.rs:63-68`

`publish()` 在**持有 `handlers` 互斥锁的情况下**逐个调用 handler：

1. 任何 handler 回调 `bus.subscribe()`（GUI 中极常见：响应 A 事件后注册 B 的回调）→ **立即自死锁**
2. 任一 handler panic → 毒化该锁 → 之后 `publish`/`subscribe`/`handler_count` 4 处 `.expect()` 全部 panic → **整个应用不可恢复**

**修复**：锁内只做 `handlers.iter().map(Arc::clone).collect()` 快照，释放锁后再逐个调用。

#### 9.3.2 P2-13 架构重构：抽出 `AppContext`

**顺带消除的重复**：CLI `script.rs` 完整复制了一份提示词拼装与 HTTP 调用，与 `use_case::script_generate` 漂移（超时 60s vs 120s、缺标题解析），已统一到用例。

**顺带修掉的死代码**：`TtsUseCase::list_voices(engine)` 零调用封装、`SynthesisSession::text_hash` 只写不读字段。

**顺带修掉的真实缺陷（`kind: Runtime` 被静默丢弃）**：

新增 ORT 清单后，`model list` 日志出现

```
[WARN] 模型清单条目无法解析，已从列表中跳过: id=onnxruntime 原因=无效的模型类型: Runtime
```

根因是 `ModelKind` 只有 `Tts/Asr/Ocr/Translation` 四个变体，
而 ONNX Runtime 动态库**不是模型**——它没有会话、没有 `load()`，
却是首次启动必须下载的运行时依赖。原设计只能把它塞进某个业务分类（语义错误）
或者让它解析失败（功能缺失）。

修复：新增 `ModelKind::Runtime` 与 `EngineKind::OnnxRuntime`，
配套 `ModelKind::is_loadable_model()`（明确「Runtime 不可 load」）
与 `display_name()`（避免各表现层重复写中文映射）。
`ProviderCapability` 同步新增 `Runtime` 变体，
避免 GUI 按能力分组时把 ORT 显示成某种业务引擎。

这个缺陷与本报告 P1-9 记载的历史 bug **完全同型**：
`parse_engine_kind` 的映射表遗漏 8 个已存在的变体，导致
`m2m-100-418m` / `hy-mt-1.5` / `cosyvoice` 三条条目被静默丢弃而退出码仍为 0。
代码注释里已写明「新增 `EngineKind` 变体时**必须同步这里**」，
但缺一个能自动发现遗漏的机制——本轮新增 3 个 domain 测试固化该契约。

**结果**：`votex-cli` 与 `votex-gui` 源码中 `votex_infra::` 出现次数归零（仅分层约束的文档注释中作为反例出现）；全工作区 `cargo check --workspace --all-targets` 达到 **0 error / 0 warning**。

### 9.4 第三轮修复（P2-17 / P2-19 及遗留安全项）

> 本轮针对上一节列出的全部 6 项未实施项，除 1 项按需调整范围外均已落地。
> 期间额外发现并修复 4 个**真实缺陷**（非代码风格问题）。

#### 9.4.1 P2-17：`load/unload` 改 `&self` + 用例共享化

**问题**：4 个 domain trait 的 `load` / `unload` 收 `&mut self`，
意味着「模型是否已加载」这一状态无法在共享引用下查询，
上层被迫持有 `Mutex<Option<T>>` 或整锁独占，用例对象无法跨线程共享。

**改动**（4 个 trait + 约 30 个引擎适配器 + 3 个 app 层用例）：

| 层 | 文件 | 改动 |
| :--- | :--- | :--- |
| domain | `tts/provider.rs`、`asr/provider.rs`、`ocr/provider.rs`、`translation/provider.rs` | `load` / `unload` 改 `&self`；`ocr` 的 `recognize` / `recognize_with_cancel` 一并改 `&self` |
| infra | `tts/indextts2.rs`、`tts/qwen3_tts.rs`、`tts/cosyvoice.rs` | `tokenizer` / `codebook` / `variant` 裸字段 → `EngineState<T>` |
| infra | `asr/paraformer.rs`、`asr/qwen3_asr.rs` | `tokens` / `tokenizer` → `EngineState<T>` |
| infra | `ocr/paddleocr.rs`、`ocr/easyocr.rs` | `variant` / `dict` / `char_dict` → `EngineState<T>` |
| infra | `translation/{opus_mt,nllb,m2m100,hy_mt,ctranslate2}.rs` | 7 处字段 → `EngineState<T>` |
| app | `tts_use_case.rs`、`asr_use_case.rs`、`ocr_use_case.rs` | 全部方法改 `&self`；`AsrUseCase::get_provider_mut` 返回 `&dyn AsrProvider` |
| app | **新增** `services/shared_cases.rs` | `OnceLock<Arc<T>>` 进程级单例，避免重复加载 GB 级权重 |

`EngineState<T>`（封装 `Mutex<Option<T>>`）成为 provider 生命周期的统一管理方式，
所有「分词/查表/解码」操作都在 `with()` 闭包内完成，**只带出 owned 数据**，
不跨锁守卫借用引用（否则触发 `cannot return value referencing function parameter`）。

**衍生收益**：GUI 每个任务原本各自 `new()` 用例 → 重复加载模型权重。
改用进程级单例后，同一进程内 TTS/ASR/OCR 权重只加载一次。

#### 9.4.2 P2-19：GUI 测试 0 → 40

**调整说明**：原计划用 `egui_kittest` 做无头渲染测试。本轮改为**把可测逻辑从 egui 中抽离**，
收益更高且不引入测试框架依赖。做法是把纯函数抽成三个独立模块，
并让 GUI 侧调用同一份实现（而非复制）：

| 新模块 | 测试数 | 覆盖内容 |
| :--- | :--- | :--- |
| `widgets/player_logic.rs` | 20 | 时间格式化、章节命中、续播位置夹取、章节文件加载 |
| `model_ready.rs` | 11 | 模型就绪判定（脱离 `OnceLock` 全局单例限制，可注入路径） |
| `cancel_contract.rs` | 9 | 取消令牌槽位契约：初始为 `None`、置位可被后台观察、`swap` 语义、页面间独立 |

`audio_player.rs` 改为委托 `player_logic`，删除本地重复实现。

#### 9.4.3 GUI「停止」贯通 `GateCancel`

**问题**：GUI「停止」按钮是**欺骗性 UI** —— ASR / OCR 页面的取消令牌只在闭包内存活
（`Some(cancel.clone())` 未写入 state），取消按钮只能改界面文字，
后台任务完全收不到取消信号。用户点「停止」后任务仍跑完全程。

**修复**：

- `state.rs`：`AsrState` / `OcrState` 新增 `cancel_token: Option<Arc<AtomicBool>>`。
- `asr_page.rs` / `ocr_page.rs`：启动时把令牌存入 state，取消按钮真正置位。
- `task_runner.rs`：`spawn_asr` 透传令牌；`spawn_batch_asr` 新增 `cancel_token` 参数。
- `app` 层：`AsrUseCase::recognize` 增加 `cancel: Option<&AtomicBool>` 参数，
  切片循环边界检查；`BatchAsrConfig` 增加 `cancel` 字段。
- CLI：`asr.rs` / `batch_asr.rs` 补 `ctrlc::set_handler`，
  用 `if !flag.swap(true, SeqCst)` 保证只提示一次。

**附带修掉的 UI 竞态**：取消时不再置 `is_running = false`
（否则下一行的 Progress 事件会覆盖「正在取消...」文字并产生
`value assigned to progress_text is never read` 警告），改由后台终态事件复位。

#### 9.4.4 存量 `.key` 权限自动收紧

**问题**：原实现只对**新生成**的密钥 `chmod 600`；
且 Windows 分支传的是 `icacls ... *S-1-5-21-*-*-*-*:F` —— **无效的 SID 通配**，
命令失败但代码只 warn，ACL 原封不动。

**实测证据**（修复前 `.key` 的 ACL）：

```
BUILTIN\Administrators:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
NT AUTHORITY\Authenticated Users:(I)(M)   ← 同机其他用户可读密钥
BUILTIN\Users:(I)(RX)
```

**修复**：存量分支也走权限收紧；Windows 分支改用 `current_windows_user()`
（`USERNAME`+`USERDOMAIN`，回退 `whoami`）得到 `DOMAIN\user`，
传 `"{user}:(F)"`，并检查 icacls 输出是否含「失败」标记。

**实测验证**（修复后）：`.key ADM\adm:(F)` —— 仅当前用户，完整控制。

#### 9.4.5 `find_onnx_file` 去除硬编码

`inference/mod.rs` 整文件重写：

- 新增 `onnx_candidates(Option<EngineKind>)`，按引擎分组给出候选文件名，
  不再硬编码 `kokoro-v1.0.onnx`。
- `find_onnx_file(model_dir, candidates)` 改为公开 API。
- **修真实缺陷**：兜底分支原来依赖 `read_dir` 的未定义顺序（同一目录多个 `.onnx` 时
  每次可能返回不同文件），改为收集全部 `.onnx` 后 `sort()` 取首个。
- 兜底时打 warn，扩展名匹配大小写不敏感，排除子目录。
- 新增 24 个测试（含「传入空候选表强制走兜底」用例）。

#### 9.4.6 模型 SHA256 全量回填（169/169）

新增 `tools/fill_sha256.py`，**只对本地真实存在的文件计算哈希，绝不臆造**。

**结果：169 个条目 100% 覆盖，本地缺失 0**（原报告估算 165，实际 169）。

**⚠️ 期间发现并修复的两个真实缺陷：**

1. **清单整体被 gitignore**：
   `.gitignore` 第 5 行 `/models/` 把 `models/registry/*.yaml`（242K 纯文本定义，
   运行时从磁盘加载，非编译期内嵌）一并忽略了。
   后果：clone 仓库后没有清单 → 模型列表为空、无法下载；
   且刚回填的 SHA256 会随本地文件一起丢失。
   已改为 `/models/*` + `!/models/registry/`，模型二进制与 ONNX Runtime 仍不入库
   （已用 `git check-ignore` 双向验证）。

2. **工具非幂等导致 YAML 重复键**：
   `fill()` 最初只在 `- name:` 的**紧邻下一行**判断是否已有哈希，
   而 `onnxruntime.yaml` 的 `sha256:` 位于 `required: true` 之后 →
   被误判为「缺哈希」而**重复插入第二行** `sha256:`。
   YAML 重复键会让 `serde_yaml` 拒绝**整份清单**，
   `ModelRegistryLoader` 对解析失败是**跳过并告警**，于是 `onnxruntime.yaml`
   整个消失（29 个文件只加载出 28 条）——
   这会让 ONNX Runtime 运行时依赖清单凭空消失，而原有守护测试**照样通过**
   （因为它只断言「清单非空」）。

   修复：工具改为先收集条目区间、剔除所有已有 `sha256:` 行，再按需插入唯一一行。
   幂等性已验证（连跑两次：回填 0 / 已有 169）。

**补强守护测试**（`model_registry_guard_test.rs` 4 → 7 项）：

| 新增测试 | 防住什么 |
| :--- | :--- |
| `registry_无清单被静默跳过` | 磁盘文件数 ≠ 解析成功数即失败 |
| `registry_条目内sha256唯一且格式合法` | 反序列化后校验 64 位十六进制 |
| `registry_原始文本无重复sha256键` | **扫原始文本**，因为 serde 会静默丢弃重复键、只留最后一个，看不出重复 |

#### 9.4.8 架构改进：消除虚假并发

`infra/ocr/batch.rs` 的 `BatchOcrOrchestrator` 持有 `Arc<Mutex<Box<dyn OcrProvider>>>`，

### 9.5 遗留技术债备忘

- **配置解析失败仍返回 `None`**：`ConfigLoader::load_optional` 在配置文件存在但 YAML 语法错误时返回 `None` 并写 stderr 提示，**不阻断启动**。这是刻意选择（配置坏了不该让用户打不开软件），已在 `platform::config` 文档与测试中明确该契约。CLI `config set/show` 走 `load_config` 路径则会明确报错。
- **`InferenceGate` 全局单例仍在**：`AppContext` 统一配置了它，但闸门本身仍是 `OnceLock` 全局。测试中可独立实例化，运行时按单例使用。
- **`qwen-mt.yaml` 声明 0 个文件**：已由 `registry_已知空文件清单` 测试显式登记为已知问题，点击下载拿不到资源，需补文件源。
- **`EngineState::get()` 返回守卫**：为避免裸引用跨越锁生命周期，`get()` 一律返回 `MutexGuard`，调用方必须在闭包内完成工作。曾尝试提供 `unsafe` 的 `try_get()` 快捷路径，已撤回 —— 不值得为省几行代码引入 unsafe。
