## 非功能性需求

### 1. 性能要求

#### 1.1 TTS 合成性能

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 实时率（RTF） | ≤ 0.5（Kokoro）/ ≤ 0.8（IndexTTS2） | 1 秒音频合成时间不超过 0.5 秒 |
| 首字延迟 | ≤ 2 秒 | 从点击合成到第一段音频输出的时间 |
| 模型加载时间 | ≤ 10 秒（Kokoro）/ ≤ 20 秒（IndexTTS2） | 引擎首次加载到就绪的时间 |

#### 1.2 ASR 识别性能

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 实时率（RTF） | ≤ 0.3（base）/ ≤ 0.6（small） | 1 秒音频识别时间不超过 0.3 秒 |
| 首字延迟 | ≤ 3 秒 | 从开始识别到第一段文本输出的时间 |

#### 1.3 内存占用

| 场景 | 上限 | 说明 |
|------|------|------|
| 空闲状态 | ≤ 200MB | 程序启动后、模型未加载时 |
| Kokoro 加载后 | ≤ 500MB | 单引擎加载 |
| IndexTTS2 加载后 | ≤ 1GB | 单引擎加载 |
| Whisper base 加载后 | ≤ 500MB | 单引擎加载 |
| Whisper small 加载后 | ≤ 1GB | 单引擎加载 |
| 合成/识别峰值 | ≤ 1.5GB | 运行时峰值 |

#### 1.4 CPU 推理调度

- 优先利用多核 CPU：ONNX Runtime 自动线程调度，默认使用 CPU 核心数 - 1 的线程数
- TTS 和 ASR 不同时执行（共用同一推理资源，避免内存峰值叠加）
- 支持用户手动设置推理线程数（通过配置文件）

#### 1.5 启动时间

- 冷启动（首次启动，无模型缓存）：≤ 5 秒（不含模型下载）
- 热启动（模型已缓存）：≤ 3 秒



### 2. 安全与隐私

#### 2.1 数据隐私

- 用户文本内容和音频文件全程本地处理，不发起任何网络上传请求
- 模型下载使用 HTTPS 加密传输
- 程序自身不收集任何用户行为数据或使用统计

#### 2.2 模型安全

- 模型下载完成后自动校验 SHA256（与官方发布的哈希值对比）
- 手动导入的模型文件也需通过 SHA256 校验（用户需提供校验文件或手动确认跳过）
- 校验失败时拒绝加载模型，提示用户重新下载

#### 2.3 临时文件

- 合成/识别过程中产生的临时音频文件存储在临时目录
- 临时文件按配置周期自动清理（默认 7 天）
- 程序退出时清理当前会话的临时文件（可选保留以便恢复）

#### 2.4 日志脱敏

- 日志中不得记录用户文本内容、音频文件路径、识别结果
- 仅记录操作类型、任务 ID、耗时、错误堆栈（不含用户数据）
- 文件名记录时仅保留扩展名和文件大小（如 `*.txt 15KB`）

### 4. 离线策略

#### 4.1 首次启动

- 检测模型是否已下载 → 未下载则引导用户下载或导入
- 无网络环境：提示用户手动下载模型文件并导入
- 提供模型下载链接（在帮助文档中，可通过浏览器打开）

#### 4.2 运行时断网

- 不影响已加载模型的使用
- 不影响音频合成、识别、导出等全部功能
- 模型下载中断：保存已下载部分，下次启动恢复下载

#### 4.3 模型更新

- 不自动检查更新，不自动下载新版本
- 用户通过模型管理界面手动触发更新
- 更新时保留旧版本，新模型下载到独立临时目录；下载失败时旧版本不受影响，用户可重试；下载成功并校验通过后替换旧版本



### 5. 错误处理

#### 5.1 错误分类

| 类别 | 示例 | 处理方式 |
|------|------|---------|
| 用户错误 | 输入文件不存在、格式不支持、参数非法 | 提示具体原因和修复建议 |
| 模型错误 | 模型未下载、校验失败、加载失败 | 提示重新下载或切换模型 |
| 系统错误 | 磁盘空间不足、内存不足、文件权限不足 | 提示原因，建议清理空间或检查权限 |
| 运行时错误 | 推理失败、ffmpeg 处理失败 | 记录日志，提示用户重试，自动重试 1 次 |

#### 5.2 错误恢复

- 任务失败自动重试 1 次（间隔 5 秒）
- 重试仍失败：标记为"已失败"，保留错误信息供用户查看
- 长文本合成失败：已完成的段落保留，支持从失败段落继续合成
- 崩溃恢复：程序异常退出后，下次启动提示恢复未完成任务

#### 5.3 错误信息

- 面向用户：简洁中文提示，说明问题和建议操作
- 面向开发者：完整错误堆栈写入日志文件，包含上下文信息



### 6. 数据持久化规范

#### 6.1 持久化文件清单

| 文件 | 格式 | 位置 | 说明 |
|------|------|------|------|
| `application.yml` | YAML | 程序同级目录 | 全局配置 |
| `tasks.json` | JSON | 程序同级目录 | 未完成任务持久化 |
| `recent_tasks.json` | JSON | 程序同级目录 | 最近任务记录 |
| `models/checksums.json` | JSON | 模型目录 | 模型哈希校验 |

#### 6.2 任务持久化格式（tasks.json）

```json
{
  "version": 1,
  "tasks": [
    {
      "id": "task-001",
      "type": "tts",
      "status": "paused",
      "input_path": "novel.txt",
      "output_path": "output.mp3",
      "params": {
        "engine": "kokoro",
        "voice": "xiaobei",
        "speed": 1.0
      },
      "completed_segments": [0, 1, 2],
      "total_segments": 12,
      "created_at": "2025-01-01T10:00:00Z",
      "updated_at": "2025-01-01T10:05:00Z"
    }
  ]
}
```

- 程序启动时检测 `tasks.json`，若存在未完成任务则提示恢复
- 任务完成或取消后从文件中移除
- 文件损坏时忽略并重建，不阻塞启动

#### 6.3 文本编码检测

- 输入 TXT 文件支持 UTF-8 和 GBK 编码
- 检测策略：优先尝试 UTF-8 解码，若失败则尝试 GBK 解码
- GBK 检测使用 `encoding_rs` 库
- 两种编码均失败时，提示用户"文件编码不支持，请转换为 UTF-8 格式"
- 检测结果记录到 DEBUG 级别日志（不记录文件内容）



### 7. 可维护性

#### 7.1 代码结构（DDD）

- 领域层：TTS 合成、ASR 识别、模型管理、任务队列的领域逻辑
- 应用层：用例编排，协调领域层和基础设施层
- 基础设施层：ONNX Runtime、sherpa-onnx、ffmpeg、文件 I/O
- 表现层：CLI（clap）和 GUI（egui/eframe），共享领域和应用层

#### 7.2 测试策略（TDD）

- 单元测试：领域层纯逻辑全覆盖（分段算法、拼接算法、配置解析）
- 集成测试：模型加载、推理流程、端到端合成/识别
- 测试数据：固定的测试音频文件和文本文件，纳入版本控制

#### 7.3 配置管理

- 所有可调参数通过配置文件暴露，不硬编码
- 配置变更无需重新编译
- 配置文件格式校验，格式错误时使用默认值并告警



### 8. 分发

- 单二进制 `votex.exe`，通过 GitHub Releases 发布
- 编译目标：`x86_64-pc-windows-msvc`
- 静态链接 CRT，不依赖 VC++ 运行时
- ONNX Runtime（通过 ort 和 sherpa-onnx）静态链接
- 二进制体积：目标 ≤ 50MB（不含模型文件）
- 模型文件独立下载，不随二进制分发
