# 21-流式语音识别 R2T2 与流式翻译 T3PO 评估分析

> 评估对象：网易有道 2026-09 开源的「子曰 Live」双模型——Confucius4-R2T2（真流式 ASR）与 Confucius4-T3PO（流式同传翻译）。
> 评估视角：① 模型本身的技术定位与实测水位；② 对 votex（CPU 离线、ONNX Runtime、4 核桌面机）的接入价值与成本。
> 信息来源：两个 GitHub 仓库 README、社区评测（2026-10-03 检索）。技术报告官方标注"will be released soon"，尚未发布。

## 1. 总体定位

两款模型是**设计好配套使用的同传级联**（命名致敬星战 R2-D2 / C-3PO）：

```
说话人音频 ──► R2T2 流式识别 ──► 稳定文本块 ──► T3PO 流式翻译 ──► 译文增量输出
              (append-only)                  (READ/WRITE 决策)
```

| | R2T2 | T3PO |
|---|---|---|
| 全称 | Real Real-Time Transcription | simulTaneous Translation via pareTo Policy Optimization |
| 任务 | 流式 ASR（语音→文本） | 流式同传（文本→文本，**不支持语音输入**） |
| 规模 | 约 1.7B（社区口径；README 未标参数量） | **14B** |
| 底座 | Qwen3-ASR（阿里通义，建模代码开源） | 未明示底座，三阶段训练（对齐数据→流式冷启动→Pareto RL） |
| 核心机制 | Longest Stable Prefix：只提交"已稳定"的前缀，**输出永不回改** | 增量决策：每步判断 READ（等更多源语）/ WRITE（出译文） |
| 延迟 | 平均 200–600ms（chunk 80ms–2s 可调，默认 160ms） | 三档 `--latency-mode low / native / high`（质量-延迟帕累托操作点） |
| 语言 | 中英为主优化，兼顾法德意日韩葡俄西阿等跨语种 | 中→英 / 英→中 双向同传 |
| 仓库 | github.com/netease-youdao/Confucius4-R2T2 | github.com/netease-youdao/Confucius4-T3PO |

## 2. R2T2：真流式 vs 伪流式

**核心差异化**是「append-only 落子无悔」。常见 pseudo-streaming ASR（含 Qwen3-ASR 朴素滑窗、Whisper 转写修正类）会回改已输出的中间结果——实时字幕表现为跳字闪烁，语音 Agent 表现为"按半句错误指令执行"。R2T2 只在模型判断某前缀足够稳定（LSP）后才提交，提交后不再改写。

**基准水位**（官方表，R2T2 @160ms）：

- 英文 WER：LS-clean 2.13 / LS-other 4.88 / TED-LIUM 3.34 / AMI 11.37 / Earnings22 9.36——在开源流式方案中**延迟-质量双 SOTA**，与商业系统（AssemblyAI 等）可比，略逊于 Qwen3-ASR 2s 伪流式上界（后者延迟高一个量级）
- 中文 CER：Wenet-meeting 7.27 / SPEECHIO-07 8.20 / CN-RealSI 3.48
- 关键对照：Qwen3-ASR base 强行 160ms 切窗 CER 高达 19.8~39.7——说明 R2T2 的价值在**训练出的稳定性判断**，而非底座本身

**工程特性**：WebSocket 服务端内置（端口 8272，增量 JSON 返回）；集成 FireRedVAD 流式 VAD；原生支持 context/热词提示；部署支持 vLLM（主推，需 NVIDIA GPU）/ transformers / llama.cpp-GGUF（三模式，社区已有 Ollama 适配）。**无官方 ONNX 导出**。

## 3. T3PO：READ/WRITE 帕累托同传

- **任务建模**：同传 = 增量决策过程。每步观察「已听到的源语前缀 + 已生成的译文前缀」，决策 READ（消费更多源语上下文）或 WRITE（自回归产出下一个目标 token）
- **训练方法**：Pareto DPO（PDPO）——把翻译质量与响应延迟作为两个独立目标，训练策略偏好"同等延迟质量更高、同等质量延迟更低"；相比 GRPO 能避免低延迟区质量坍缩
- **推理协议**：interleaved history 组织输入序列，支持 KV-cache 复用；接收细粒度文本块（如逐词）流式喂入；会话制（session_id），结束需 `end=true` flush
- **实测亮点**（媒体评测）：说话人改口（"上午十点，哦不对，下午两点"）能像人类同传一样补救；财报数字等完整数字说完才开口，数字零错
- **评测**：中英双向同传 vs 开源 InfiniSST / EAST 与两个商业同传系统，COMET vs word-CW 帕累托前沿占优（官方图，具体数值表未随 README 发布）
- **规模 14B**——这是对 votex 最关键的数字

## 5. 对 votex 的接入评估（核心结论）

结合 votex 约束：**CPU 离线（无 GPU）、4 核老平台（i7-4710MQ 实测约 20GB 内存）、底层统一 ONNX Runtime、单二进制、模型独立管理**。

### 5.1 R2T2

| 维度 | 评估 |
|---|---|
| 能力匹配 | ★★★★☆ 流式 ASR 正是「实时字幕 / 听读一体同步高亮 / 同传前端」需要的能力；append-only 特性与字幕 UI 天然契合（不闪烁） |
| 运行时 | ★★☆☆☆ 官方三路部署（vLLM/transformers/llama.cpp）**均非 ONNX**；llama.cpp-GGUF 可 CPU 但量化精度与延迟需实测 |
| 算力 | ★★☆☆☆ 1.7B LLM 架构逐 chunk 连续解码：参考同机 CosyVoice LLM 138ms/步（4 核），R2T2 每步 decode + encoder 开销下，200–600ms 官方延迟在 GPU 上成立，本机 CPU 实际可达延迟预估秒级——**超出"实时"体验红线** |
| 集成成本 | ★★☆☆☆ 需自建音频流循环（现有 ASR 管线是整段离线式）+ llama.cpp 侧车或 ONNX 自行导出（Qwen3-ASR 架构导出社区尚无成熟方案） |
| 许可 | 权重非 Apache，需法务确认 |

**结论：不建议当前接入；作为「实时字幕/同传」特性的候选跟踪项。** 若 votex 未来做实时字幕，短期更现实的路径是评估 sherpa/WeNet 的流式 Conformer（CPU 原生、ONNX 化成熟），R2T2 作为质量上限参照。

### 5.2 T3PO

| 维度 | 评估 |
|---|---|
| 能力匹配 | ★★★☆☆ 流式翻译对「边听边译字幕」有价值，但 votex 现有场景（有声书/视频配音）以整段离线翻译为主，流式非刚需 |
| 算力 | ★☆☆☆☆ **14B**——4 核 CPU 桌面机完全不可行；GGUF 量化后仍需 8GB+ 内存且 decode 秒级 |
| 集成成本 | 同传协议（会话 + 流式 chunk + flush）与现有 batch translate 管线形态差异大 |

**结论：不接入。** 对比参考：votex 已集成的 HY-MT-1.5（离线整句，质量工程已验证）覆盖现需求；若未来需要 GPU/云端同传特性，T3PO 是开源首选之一（帕累托可调 + 改口补救是独有卖点）。

### 5.3 可借鉴的设计（零成本收益）

1. **append-only 提交策略**：votex 未来做实时字幕 UI 时，可在任意 ASR 引擎外包一层"稳定前缀"提交逻辑（n-best 置信度 + 停顿启发式），低成本获得不闪烁体验
2. **热词/context 提示**：R2T2 原生支持技术词汇注入，与 votex 翻译模块的术语表（glossary）机制同构，可对照设计 ASR 热词接口
3. **质量-延迟档位暴露**：T3PO 的 low/native/high 三档是对用户暴露"快慢选择"的好范式，votex pipeline 可借鉴为预设档
