## 1. 目的与原则

### 1.1 目的

验证 TTS、ASR、翻译、OCR 四条主功能链路**在真实模型、真实文件、真实进程边界上端到端可用**，并验证它们在流水线中相互衔接的能力（TTS→ASR 闭环、OCR→翻译→TTS 有声书链路、ASR→翻译 字幕链路）。

本计划与单元/集成测试的分工：

| 层次 | 关注点 | 本计划是否覆盖 |
|---|---|---|
| 单元测试 | 领域对象、算法（分段、数字转中文、G2P、标点、术语表、简繁） | 否（`cargo test` 覆盖） |
| 集成测试 | 单个 provider 加载模型并完成一次推理（`crates/votex-infra/tests/*`） | 否，但作为 E2E 前置门禁（**注意 §11-F26：该目录当前无法整体编译**） |
| **E2E 验证** | **`votex.exe` 进程 + `application.yml` + `models/` + 真实输入文件 → 产物文件内容** | **是（本计划）** |

### 1.2 原则

1. **进程级验证**：一律通过 `votex.exe` 子进程调用，断言退出码、stdout/stderr、产物文件，而不是直接调用 Rust API。集成测试证明 provider 可用，E2E 证明"装配后的产品"可用——**本次调研已抓到多个"provider 通、CLI 崩/静默降级"的实例（F1、F8、F9、F13、F14）**，正是 E2E 的价值所在。
2. **可量化断言**：每个用例给出明确判据（相似度阈值、字段存在性、时长误差、格式校验），禁止"跑通即通过"。
3. **禁止静默跳过**：模型缺失、素材缺失一律判 **阻塞（Blocked）**，并在报告中写明缺失路径。现有集成测试大量使用"缺失即 `return`"（F27），已掩盖多项交付缺陷；E2E 层必须反向而行。
4. **负向用例同等重要**：非法参数、语言不支持、模型缺失时的行为（明确报错 vs 静默降级 vs 崩溃）必须纳入断言。
5. **优先级驱动**：`P0` 发布阻断、`P1` 交付质量、`P2` 体验/边界。
6. **对等性验证**：CLI 与 GUI 共用领域层，CLI 为基准，GUI 每条主链路抽 1 个冒烟用例（§9.2）。
7. **敏感信息零落盘**：产物、日志、断言消息中不得出现 API Key、手机号、身份证号（遵循 `00-安全设计.md`）。

#### G0-12：registry ↔ 磁盘一致性脚本（v1.2 新增，可直接执行）

> 目的：保证 `models/registry/*.yaml` 声明的每个文件都真实存在于磁盘，杜绝"下载成功但运行时永不加载"（F45）与"代码期望名与 registry 声明名不符"两类问题。
> 白名单：`qwen-mt` 为在线模型（`DASHSCOPE_API_KEY`），无本地目录属预期。

```powershell
# G0-12 registry 一致性（PowerShell 5.1+，在仓库根执行）
$bad = @(); $okCount = 0
$WHITELIST = @('qwen-mt')   # 在线模型，无本地目录

foreach ($f in Get-ChildItem "models\registry\*.yaml" | Sort-Object Name) {
  $id = $null; $kind = $null; $sub = $null
  $names = @(); $inFiles = $false
  foreach ($l in Get-Content $f.FullName -Encoding UTF8) {
    if ($l -match '^files:\s*$') { $inFiles = $true; continue }
    if ($inFiles) {
      if     ($l -match '^\s+-\s+name:\s*(.+?)\s*$') { $names += $Matches[1].Trim('"',"'"); continue }
      elseif ($l -match '^\S')                            { $inFiles = $false }
    }
    if     ($l -match '^id:\s*(.+?)\s*$')      { $id   = $Matches[1].Trim('"',"'") }
    elseif ($l -match '^kind:\s*(.+?)\s*$')    { $kind = $Matches[1].Trim('"',"'") }
    elseif ($l -match '^sub_dir:\s*(.+?)\s*$') { $sub  = $Matches[1].Trim('"',"'") }
  }
  if ($WHITELIST -contains $id) { "SKIP [$id] 在线模型（白名单）"; continue }
  if (-not $sub) { $sub = $id }
  $bucket = switch ($kind) {
    'Tts'{'tts'} 'Asr'{'asr'} 'Ocr'{'ocr'} 'Translation'{'translation'} default{'?'}
  }
  $dir = "models\$bucket\$sub"
  if (-not (Test-Path $dir)) { $bad += "[$id] 目录不存在: $dir"; continue }
  foreach ($n in $names) {
    if (Test-Path (Join-Path $dir $n)) { $okCount++ } else { $bad += "[$id] 缺文件: $n" }
  }
}
"已校验通过文件数: $okCount"
if ($bad.Count -eq 0) { "`n✅ registry 与磁盘完全一致" } else { "`n❌ 剩余 $($bad.Count) 项不一致:"; $bad | ForEach-Object { "   $_" }; exit 1 }
```

**基线（2026-10-02 修复后实测）**：`已校验通过文件数: 165`，`✅ registry 与磁盘完全一致`（`qwen-mt` 走白名单）。

#### G0-14：下载镜像 HEAD 探测脚本（v1.2 新增，仅下载类用例需要）

```powershell
# G0-14 探测 registry 中所有 sources URL 的可达性
$dead = @(); $live = 0
foreach ($f in Get-ChildItem "models\registry\*.yaml") {
  $lines = Get-Content $f.FullName -Encoding UTF8
  $cur = $null
  for ($i = 0; $i -lt $lines.Count; $i++) {
    $l = $lines[$i]
    if ($l -match '^\s+-\s+name:\s*(.+?)\s*$') { $cur = $Matches[1]; continue }
    if ($l -match '^\s+(huggingface|hf-mirror|modelscope|github|gitee):\s*(\S+)') {
      $u = $Matches[2]
      try {
        $r = Invoke-WebRequest -Uri $u -Method Head -TimeoutSec 20 -MaximumRedirection 5 -UseBasicParsing
        if ($r.StatusCode -eq 200) { $live++ } else { $dead += "$($f.Name) [$cur] $($Matches[1]) -> HTTP $($r.StatusCode)" }
      } catch {
        $code = if ($_.Exception.Message -match '\((\d{3})\)') { $Matches[1] } else { 'ERR' }
        $dead += "$($f.Name) [$cur] $($Matches[1]) -> $code"
      }
    }
  }
}
"可达源: $live ; 失效源: $($dead.Count)"
$dead | ForEach-Object { "   $_" }
```

**注意**：`huggingface.co` 直连不通（实测 2026-10-02 `TcpTestSucceeded=False`），但 `hf-mirror` 可用 → 探测 `huggingface` 源 404/超时属**环境限制**，不计入缺陷；只有 `hf-mirror`/`modelscope`/`github`/`gitee` 失效才登记为 F52 类缺陷。

### 6.1 覆盖与通用判据

**关键约束（必读）**：

1. **只吃 WAV**（且扩展名必须小写 `.wav`）。非 wav 输入**不报错**，而是 warn + 按静音处理（`asr_use_case.rs:182-202`）→ MP3/M4A/FLAC/MP4 用例必须**先用 ffmpeg 转 WAV**，否则"成功"是假象（F36）。
2. **`--lang` 无效**：所有 provider 忽略 `AsrParams`；Whisper 恒按 `zh` 解码，SenseVoice 恒 `auto`（F34）→ 不做"语种切换"断言，只做"参数不生效"的登记用例。
3. **时间戳为切片级**：`word_timestamps` 全为 0，`AsrUseCase` 按 30 秒切片累加（`asr_use_case.rs:104-125`）→ SRT/LRC 断言按"切片边界"口径，不做词级对齐断言（F35）。
4. **末片可能越界**：最后一片 end_time 用整片时长 → 可能超出音频实际长度（F35）。
5. 可用模型：`sensevoice`、`whisper-base`、`firered-asr`(CTC)、`wenet`；**不可用**：`whisper-small`、`paraformer`、`qwen3-asr`（F32/F33）。

**已实测基线**：`asr -i tmp/e2e_tts_probe.wav.wav -o target/e2e_asr_probe.txt --model sensevoice --format txt --lang zh`
→ 退出码 `0`，`字幕条目: 7 条`，识别出 3455 字 TTS 音频的大段文本（有明显同音错字，如"张重→张仲"），**闭环方向正确**。

通用判据：

| 判据 | 内容 |
|---|---|
| 退出码 | `0`，且不得为 `-1073741819` |
| 产物 | 输出文件存在且非空 |
| 中文识别 | 去标点内容覆盖率 ≥ 70%（真值已知时） |
| 英文识别 | 单词匹配率 ≥ 70% |
| 时序 | SRT 格式 `HH:MM:SS,mmm`；时间戳单调不减；末条结束时间 ≤ 音频时长 × 1.05（容忍末片越界），且 ≥ 音频时长 × 0.8 |
| 编码 | 输出 UTF-8，无乱码 |

### 8.2 质量评估方法（项目无自动指标，需替代方案）

现有测试仅验证"能翻译"（非空、语向正确、少量 golden）。**全仓库不存在 BLEU / COMET / chrF / 回译机制**（F4）。因此本计划采用三层评估：

| 层级 | 方法 | 阈值 |
|---|---|---|
| L1 结构正确性 | 语向正确、非空、无 `<unk>`/特殊 token 泄漏、长度比合理（zh→en 字符数比 1:1.5~1:4） | 100% 通过 |
| L2 关键信息保持 | 数字、专有名词、术语表词条必须保留或按术语表译出（`2024年`→含 `2024`；`爱丽丝`→`Alice`） | 数字保持率 100%，术语命中率 100% |
| L3 语义质量抽检 | 每引擎抽 20 句，人工 5 分制 | 平均 ≥ 3.5，无 1 分句 |

**建议增强（P2）**：引入 **chrF**（字符级 n-gram F 值，无需训练、适合中文）作为 CI 可跑的自动指标，zh→en 阈值 chrF ≥ 0.55。

### A.1 PowerShell / 终端陷阱（v1.3 新增，v1.4 续增 3 条，全部实测踩过）

> 这一节是本轮排查 F56 时浪费最多时间的坑，**每一条都会导致"假缺陷"或"假失败"**。
>
> **一条通用原则：看到"不可能的结果"（乱码、语法错误位置离谱、除零、缓冲区永远为空），先怀疑终端与脚本编码，再怀疑被测代码。** 本节 11 条里有 5 条纯粹是终端问题，**零条是产品缺陷**。

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **UTF-8 无 BOM 被按 GBK 解码** | 用 `Get-Content` / `Select-String` 读日志或文档，中文**全部显示为乱码** → 曾据此误判为缺陷 **F56** | `[System.IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)`；或用 `read` 工具 / 字节级校验。**看到中文乱码先怀疑终端，不要怀疑文件** |
| **命令行里的中文字面量被污染** | 在 `powershell -Command` 中传中文串（如 `"日志系统初始化完成"`）后 `Contains` 恒为 `False` | 改用 `[char]0x65E5` 之类的码点构造，或写成 `.ps1` 文件（纯 ASCII 源码，无 BOM 问题）。**验证含中文的匹配不要用命令行字面量** |
| **`String.IndexOf` 与 `Contains` 不一致** | `Contains` 返回 `True` 但 `IndexOf` 返回 `-1`（文化相关比较 vs 序号比较） | 判定内容存在性一律用 `String.Contains`（序号比较），不要用 `IndexOf` 判存在 |
| **`cargo ... 2>&1 \| Select-String` 报 `Exited with code 1`** | 明明 `Finished`/全 passed，PowerShell 却报退出码 1 | `cargo` 的 warning 写 stderr，被 `2>&1` 合并后 PowerShell 视为 `NativeCommandError`。**先看输出内容里的 `test result`/`Finished` 再判成败**；加 `$ErrorActionPreference='Continue'` |
| **exe 被运行中进程占用** | `cargo build --release -p votex` 报 `failed to remove file` | **等进程退出再重建**（本轮曾因此阻塞约 40 分钟）；临时可用 `target\release\deps\votex.exe`。**绝不要在占用期间下"修复无效"结论** |
| **curl 进度条写 stderr** | PowerShell 把 curl 的正常输出当错误 | `curl --silent --show-error` + `$ErrorActionPreference='Continue'` |
| **日志被长任务刷屏** | 一次 CosyVoice 长 TTS（每 token 2 条 INFO）产出 7,885,870 字节日志，**挤成一行**（F58） | 已由 F58 修复（按行分隔）；排查前先按日期/大小挑当日文件 |
| **`.Contains` 判定 UTF-8 合法性不足** | 某些非法序列也会被替换字符吞掉 | 用 `New-Object System.Text.UTF8Encoding($false,$true)` **严格解码**，再把解码结果重新编码与原始字节逐字节比对 |
| **`.ps1` 脚本里的中文被 GBK 二次污染（v1.4 复现）** | 用写文件工具创建**无 BOM** 的 `.ps1`，其中含中文串或中文路径 → `powershell -File` 直接**语法错误**（`ParserError` / `缺少右括号`），且报错位置在**看起来正常**的 `foreach`/`Write-Host` 行，极难定位 | `.ps1` 源码保持**纯 ASCII**：中文路径用 `Get-ChildItem -Filter '20-*.md'` glob 定位，中文串用 `[char]0x65E5` 构造；或给 `.ps1` 加 UTF-8 BOM 让 PS 5.1 正确识别 |
| **长任务的输出被 `Out-String` 缓冲** | 后台跑 CosyVoice 类长命令时，管道到 `Out-String` 导致**中间过程完全不可见**（文件 0 行），只能等结束才知道进度 | 中途要看进度就**不要**接 `Out-String`；改为结束后一次性落盘，或直接观察产物目录 `segments/*.tmp.wav` 的字节数增长 |
| **WAV 头不能用固定偏移解析** | 按 `12+8+16` 硬算 `data` 偏移，遇到带 `LIST`/额外 chunk 的文件会读出 `sr=65537`、`ch=0` 并触发除零 | 逐 chunk 扫描（读 4 字节 id + 4 字节 size 再跳），本项目产出的 WAV 恰好是标准 `RIFF/fmt (16B)/data` 三块结构 |

### 14.3 音频取证（RIFF chunk 逐块扫描）

| 产物 | fmt | 声道 | 采样率 | 位深 | data 采样点 | 时长 |
|---|---|---|---|---|---|---|
| kokoro `audiobook` tiny | PCM(1) | 1 | 24,000 | 16 | 88,800 | **3.700 s** |
| cosyvoice3 `audiobook` tiny | PCM(1) | 1 | 24,000 | 16 | 153,616 | **6.401 s** |
| cosyvoice3 `audiobook-sub` 141 字 | PCM(1) | 1 | 24,000 | 16 | 1,468,720 | **61.2 s** |

> 两者均为标准 `RIFF/WAVE/fmt /(16 字节)/data` 结构，无 `LIST` 等额外 chunk。
>
> ⚠️ **但「格式正确」完全不能证明「功能可用」**：cosyvoice3 的两个产物格式完全合规、时长合理（≈0.43 s/字），**ASR 闭环却证明音频内容与输入文本无关**（见 14.4 / F67）。**这是本轮最重要的方法论教训：TTS 产物必须做内容级验证（ASR 回环比字），只验 RIFF 头会把「能产出合法 WAV」误判为「合成正确」。**

### 14.6 回归门禁缺口（本轮方法论缺陷）

> 本轮我第一次只验了 WAV 头就判定 CosyVoice3「F62 已修、可跑通」，**漏掉了内容验证**。同类风险在既有测试里同样存在：`tts_e2e_multi_engine_test.rs`（§11.2）对 cosyvoice3 的断言是「识别非空 + 覆盖率 >30%」——按此断言，F67 的产物**本应被判定为失败**。它之所以没报警，是因为该测试长期静默跳过（§11.2 已记录）。
>
> **建议纳入门禁（待产品确认）**：TTS 产物质量断言必须包含「ASR 回环内容覆盖率」，且**模型缺失时直接 panic 而非跳过**（`tts_asr_闭环_test.rs` 已是正确范式：3 passed / 覆盖率 71.4%）。

### 14.7 F67 根因调查记录（v1.5）

调查用**可证伪的对照实验**推进：每次只改一个变量 → release 构建 → 15 字文本合成 → SenseVoice 回环读内容。共 3 轮。

| 轮次 | 变量 | 生成 token | 采样点 | ASR 识别结果 | 判读 |
|---|---|---|---|---|---|
| A（原始） | 温度 0.9 + 重复惩罚 1.3 + prompt 惩罚 1.2 + `“”` 包裹 | 160 | 153,616 | `黄昏的海边浪花。` | ❌ **输出 = prompt 文本** |
| B | 把 SOS 与文本位置对调（**错误假设**） | 139 | 133,456 | `我嗯相知度爱那好。` | ⚠️ 泄漏消失但内容仍错 → 假设被否，**回滚** |
| C | 恢复官方纯 top-k + 移除 `“”` 包裹 | 150 | 144,016 | `嗯听党建建一打。` | ⚠️ 同上 → 惩罚项**不是**根因 |

> 轮次 B/C 的共同现象值得注意：**一旦偏离官方参考，prompt 泄漏就消失，但内容始终是乱码**。说明文本条件通路本身是通的（模型确实在响应输入），只是产出的语音 token 不对应输入的字。

#### 已排除的假设（逐项附证据）

| # | 假设 | 排除方式 | 证据 |

| 2 | LLM 输入序列布局与官方不一致 | 与 `onnx_inference_pure.py:396` 逐行比对 + 轮次 B 实验 | 官方即 `[sos_emb, text_emb, task_id_emb, prompt_speech_emb]`，**原实现本就正确**；轮次 B 对调后实测更差 |

#### 唯一可量化的异常

分段量纲（release 日志，`cosyvoice:680`，已降为 `debug!`）：

| 分段 | shape | **RMS** | min | max |
|---|---|---|---|---|
| `text_emb` | [57, 896] | **0.0223** | -0.1231 | 0.0958 |
| `sos_emb` | [1, 896] | 0.9393 | -3.2715 | 2.6855 |
| `task_id_emb` | [1, 896] | 0.8900 | -2.5762 | 2.3496 |
| `prompt_speech_emb` | [201, 896] | 0.8890 | -3.7695 | 3.5312 |

文本嵌入比其余三段小 **40 倍**。另一项佐证：**7 次不同文本的 `text_emb` 的 `min` 精确到小数点后 8 位相同**（`-0.12306465`，6 次完全一致），只有 `mean` 微变 —— 提示该张量由「大量固定分量 + 少量变化分量」构成。

**但这不足以定罪**：`text_embedding_fp32.onnx` 只有 1 个输出、量级由模型导出时决定，而官方 Python 参考同样取 `outputs[0]`，因此**官方链路的文本嵌入很可能也是这个量级**。要确认必须跑官方脚本比对，而这需要 Python。

#### 阻塞点与决策请求

本机 **没有 Python**（`python` / `python3` / `py` 三个入口均不存在，也没有 `onnxruntime`），因此**无法产出官方基准音频做逐段 diff**。在没有基准的情况下继续改 `flow_inference` / `hift_inference` / 特征提取（合计数百行）属于盲改，失败时无法区分「改对了」与「换了一种错」。

**请产品决策 F67 的处置范围**：

| 方案 | 内容 | 代价 / 风险 |
|---|---|---|
| **A** | 反向工程余下推理实现（Flow / HiFT / 特征提取） | 高风险：无基准，盲改；RTF≈18 的前提下每次验证 ~2 min，迭代慢 |
| **B** | 装 Python + `onnxruntime` 跑 `onnx_inference_pure.py` 建立基准音频，再逐段 diff | 需装解释器与依赖（可离线）；一旦有基准，A 的每一步都能被验证，**推荐** |
| **C** | 暂把 CosyVoice3 标记为**实验性**，在 CLI 帮助 / GUI 引擎下拉 / 文档三处明确「输出内容不可信」，优先保障 kokoro 与 indextts2 | 立即止血；但 E2E-PL-02 的 5 引擎矩阵只能按 2 引擎执行 |

> 在方案确定前，**不建议**把 CosyVoice3 纳入任何交付场景或回归门禁的必过项。
