# 一、ebook2audiobook 是什么

DrewThomasson/ebook2audiobook（Apache 2.0，日期式版本号 v26.9.27，高频迭代）：
目前最完整的**本地化电子书转有声书**开源方案。完整管线：

```
电子书输入(20+格式) → 文本提取 → 章节检测切分(epub/mobi 最佳)
→ 句子级分段(按语言调优) → TTS 逐段合成(audio chunks)
→ 拼接封装 → m4b 带章节标记与元数据输出
```

核心能力：零样本语音克隆（1~5 分钟参考音频 + 自动降噪）、SML 文本级
停顿标签（`[break]`/`[pause:N]`/`[voice:...]`）、**`--session` 断点续转**、
Audiobookshelf 直连、CPU/GPU/CUDA/ROCm/XPU/MPS 多后端（最低 2GB RAM / 1GB VRAM）。

# 二、对 votex 的可借鉴点（按价值排序）

## ★★★ 1. 会话断点续转（--session 机制）

E2A 每本书一个 session 目录，中间产物（音频 chunks、进度状态）落盘；
中断/崩溃后恢复会话，**已合成的段不重算**。

**votex 现状**：批量 TTS 链路完全不写 `tts_tasks` 表（CLI `batch_tts` 与
GUI `spawn_batch_tts` 均绕过 TaskManager），进程退出全部丢失。一本 10 万字
的书合成到 80% 崩溃 = 从零再来。

**借鉴方案**：长文本任务引入 `task_id` → 每段音频立即落盘为
`tmp/sessions/{task_id}/seg_{n:05d}.wav` + 进度 JSON；恢复时扫描已存在
分片跳过。这是有声书场景价值最高的单点改造。

## ★★★ 2. 中间产物落盘 + 流式拼接（内存治理）

E2A 用「chunk 落盘 → 最终合并」而非全量内存驻留。

**votex 现状**（缺陷证据）：
- `WavWriter::write_concat`（wav.rs:94-117）把所有段 f32 **先合并成巨大
  Vec 再整体转 i16**：10 小时 @24kHz 有声书 ≈ f32 3.4GB + i16 副本 1.7GB
  + 转换中转 1.7GB ≈ **6GB+ 内存峰值**；MP3 路径 `concat_and_encode_to_mp3`
  再独立做一遍全量拼接。
- 每段合成结果一直持有在 `Vec<AudioData>` 中直到任务结束。

**借鉴方案**：段完成即写盘；拼接阶段逐段读文件 → 追加写（WAV 可直接
流式追加，RIFF 头最后回填 size）；MP3 用 ffmpeg `concat demuxer` 对文件
列表操作，避免全量驻留。

## ★★☆ 3. SML 文本级停顿控制

E2A 在文本层支持 `[break]`（0.3~0.6s 随机）、`[pause]`（1.0~1.6s）、
`[pause:N]`（固定 N 秒）、`[voice:...]` 多音色。

**votex 现状**：`TtsParams.segment_silence_ms=300` / `crossfade_ms=50`
在 `tts_use_case.rs:102-103` 被赋值后**全仓库无任何消费点**——`write_concat`
是裸首尾相接，段边界韵律断裂、爆音风险。

**借鉴方案**：先让 `segment_silence_ms` 真正生效（拼接时插入静音段），
再考虑支持用户文本内联 `[[pause:1.5]]` 标签（解析层转换，与领域层解耦）。

## ★★☆ 4. 章节感知切分

E2A 依赖 epub/mobi 结构元数据做章节检测，输出 m4b 保留章节标记。

**votex 现状**：`TextSegmenter` 完全无章节感知——「第X章」、标题、空行
结构与普通句子一视同仁；`preprocess`（去空行）只在 pipeline 用例被调用，
TTS 主链路根本没走。

**借鉴方案**：`Segmenter` 增加章节层（正则识别 `第[一二三...\d]+[章节回卷]`
+ Markdown 标题），章节边界强制切分段并插入长静音；未来输出 m4b 章节表
（需要 ffmpeg metadata，或先用 Audible 兼容的 mp3 + chapters.txt）。

## ★★☆ 5. 断点可取消 + 硬件门槛自适应

E2A：GUI 取消即时生效；`--device` 缺省自动回退 CPU；官方按 RAM/VRAM
给最低/推荐档位，CPU 用户被建议换轻量引擎（YourTTS/Tacotron2）。

**votex 现状**：GUI cancel_token **只在任务开始前检查一次**，合成循环内
从不检查——点「取消」后后台仍把整本书合成完；且「取消」按钮根本没把
token 传给已 spawn 的任务（task_runner.rs:59-64、tts_page.rs:181-184）。

## ★☆☆ 6. 其它

- **自动降噪参考音频**（DeepFilterNet）→ votex 已有 denoise 能力，可复用到
  语音克隆参考音频预处理（未来克隆功能）。
- **每本书映射不同音色**（voice_map JSON）→ votex `batch tts` 已支持
  Tab 分隔的逐行音色，方向一致，可补 JSON 配置形式。
- **多引擎按语言自动匹配** → votex 可按文本语言检测结果自动选引擎/音色。

**不借鉴**：E2A 的 Python + Gradio + 依赖 Calibre/ffmpeg 外部安装的形态，
与 votex 单二进制约束冲突；其 28 个引擎路线图同样是数量堆砌。

# 四、资源监控与自适应调度设计（问题三）

## 4.1 设计目标

长文本批量合成时：**不触发 OOM/宕机/hang；资源富余时不浪费；用户无感**。

## 4.2 三层治理架构

```
┌─ 第 1 层：资源感知 ResourceMonitor ─────────────┐
│  sysinfo crate 500ms 采样：可用内存/总内存、      │
│  CPU 使用率、进程自身 RSS、内存压力分级           │
│  Green(<60%) / Yellow(60-80%) / Red(>80%)       │
└──────────────┬──────────────────────────────────┘
               │ 快照（原子变量，无锁读取）
┌─ 第 2 层：全局推理闸门 InferenceGate ────────────┐
│  ① 全局模型句柄注册表：同引擎全进程只加载 1 份     │
│     （Arc 引用计数，引用归零卸载，LRU 上限 N 份）  │
│  ② 信号量限流：并发合成段数 = f(内存压力)          │
│     Green=配置值(默认2) Yellow=1 Red=排队等待     │
│  ③ 提交前预检：预估段内存 + 当前 RSS > 安全水位    │
│     → 拒绝/等待，不盲目接单                       │
└──────────────┬──────────────────────────────────┘
               │
┌─ 第 3 层：段级执行器自适应 ──────────────────────┐
│  · 段时长监控：单段耗时 > 5×滑动平均 → 判定 hang   │
│    （日志 + 看门狗线程，可选 abort）              │
│  · 批量循环内每段检查 cancel_token（可取消）       │
│  · 内存 Red 时：暂停派发 + 已派发段完成后落盘释放   │
│  · 长任务周期性 checkpoint（配合断点续转）         │
└─────────────────────────────────────────────────┘
```

## 4.3 关键接口草图（Rust）

```rust
// votex-infra/src/shared/resource_monitor.rs
pub struct ResourceMonitor { /* sysinfo */ }
pub enum MemoryPressure { Green, Yellow, Red }
impl ResourceMonitor {
    pub fn snapshot(&self) -> Snapshot;          // 可用内存MB / RSS / CPU%
    pub fn pressure(&self) -> MemoryPressure;    // 分级
}

// votex-infra/src/shared/model_registry.rs —— 全局单例模型池
pub struct ModelRegistry {
    entries: Mutex<HashMap<EngineKey, Arc<ModelHandle>>>,
    max_loaded: usize,               // LRU 上限，默认 2
}
impl ModelRegistry {
    pub fn acquire(&self, key: EngineKey) -> Arc<ModelHandle>; // 引用计数
    // 引用归零 → 入 LRU；超上限卸载最旧（禁止自动删模型文件，仅卸内存）
}

// votex-app/src/services/inference_gate.rs —— 并发闸门
pub struct InferenceGate {
    sem: tokio::sync::Semaphore,     // 或 crossbeam + std::thread 场景自实现
    monitor: Arc<ResourceMonitor>,
}
impl InferenceGate {
    // 信号量额度随内存压力动态调整：Green=N, Yellow=1, Red=0(等待)
    pub async fn acquire_permit(&self) -> Permit;
    // 提交前预检：need_mb = 模型固定占用 + 段音频估算
    pub fn can_admit(&self, need_mb: u64) -> bool;
}
```

## 4.4 配置接入（application.yml）

```yaml
resource:
  monitor_interval_ms: 500
  memory_pressure_red_pct: 80      # 可用内存占比低于此 → Red
  memory_pressure_yellow_pct: 60
  max_loaded_models: 2             # 全局同时驻留模型份数上限
  max_inference_concurrency: 2     # Green 状态下的合成并发
  watchdog_segment_timeout_ms: 300000   # 单段判 hang 阈值
  enforce_limits: true             # false = 关闭治理（调试用）
```

## 4.5 与现有机制的衔接

- `InferenceConfig.num_threads` 已生效 → 闸门层保证「模型份数 × num_threads
  ≤ 物理核数」，即 `max_inference_concurrency` 默认值可由
  `available_parallelism() / num_threads` 自动推导，用户配置仅作覆盖。
- `memory_limit_mb` 目前只设 `ORT_ENABLE_MEMORY_ARENA=0` 环境变量（非真上限），
  治理层改为提交前预检的真实拦截点。
- 模型池已解决翻译侧重复加载（`TranslationModelPool`），TTS 侧复用同一
  `ModelRegistry` 抽象即可，不重复造轮子。

# 附：为什么不是照搬 E2A

E2A 的价值在「管线工程」（session 续转、chunk 落盘、章节感知、SML），
这些是**语言无关的架构思想**，votex 用 Rust 可以做得更省内存。而它的
Python 技术栈、外部依赖安装器、Gradio 形态、引擎数量堆砌均不适用。
