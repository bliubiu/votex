## 模型规范

本文档定义 votex 使用的所有离线模型的文件结构、下载源、校验方式和音色列表。



### 模型文件管理

#### 目录结构

模型文件统一存储在项目根目录的 `models/` 下，按 TTS/ASR/OCR 分类存放。

```sh

│   ├── kokoro-82m.yaml       # 每个模型一个清单文件

│   ├── indextts2.yaml
│   ├── whisper-base.yaml
│   ├── whisper-small.yaml
│   ├── sensevoice.yaml
│   ├── paddleocr-v6-tiny.yaml
│   ├── paddleocr-v6-small.yaml
│   └── ...                   # 其他模型清单
│
├── tts/
│   ├── kokoro-82m/           # Kokoro-82M ONNX 模型
│   ├── cosyvoice/            # CosyVoice 3.0 模型
│   ├── qwen3-tts/            # Qwen3-TTS 模型
│   └── indextts2/            # IndexTTS2 模型
├── asr/
│   ├── whisper-base/         # Whisper base 模型
│   ├── whisper-small/        # Whisper small 模型
```

#### 模型清单（registry）

每个模型在 `models/registry/{id}.yaml` 中定义其文件列表和下载源。清单文件由配置文件 `application.yml` 中的 `models.registry_path` 指定目录，默认 `models/registry`。

```yaml
# models/registry/kokoro-82m.yaml 示例
id: kokoro-82m
name: Kokoro-82M
kind: Tts
engine: Kokoro
files:
  - name: kokoro-v1.0.int8.onnx
    sha256: "abc123..."
    sources:
      huggingface: "https://huggingface.co/.../kokoro-v1.0.int8.onnx"
      modelscope: "https://modelscope.cn/.../kokoro-v1.0.int8.onnx"
  - name: voices/af_heart.bin
    sources:
      huggingface: "https://huggingface.co/.../voices/af_heart.bin"
      modelscope: "https://modelscope.cn/.../voices/af_heart.bin"
```

- 清单文件定义模型的身份、类型、所需文件及每个文件在各镜像源的下载地址
- `MirrorResolver` 根据配置文件中的 `download.priority` 列表，按优先级为每个文件选择下载源
- 镜像名与 `sources` 中的键对应（如 `huggingface`、`modelscope`、`hf-mirror`、`github`）
- `sub_dir` 字段可覆盖存储子目录（例如多个模型共享同一目录）
- `tokenizer` 是可选的**分词器配置**字段（v0.1.1+），用于处理 HuggingFace 与原始 SentencePiece 之间 ID 映射不一致的特殊情况：

```yaml
# NLLB-200 示例：HuggingFace NllbTokenizer 重排了特殊 token，
# 导致内容 token ID 偏移 +1
tokenizer:
  type: sentencepiece            # 分词器类型（可选）
  id_offset: 1                   # 内容 token ID 偏移量（NLLB 特有）
  eos_on_input: true             # 编码器输入末尾是否自动追加 EOS
  decoder_start_token: eos       # 解码器起始 token 类型
  added_tokens:                  # 附加 token（如 FLORES-200 语言代码）
    eng_Latn: 256047
    zho_Hans: 256200
    zho_Hant: 256201
```

**`tokenizer` 配置字段说明：**

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `type` | string | `"sentencepiece"` | 分词器类型，当前仅支持 `sentencepiece` |
| `id_offset` | integer | `0` | 内容 token ID 偏移量。某些模型（如 NLLB）的 HuggingFace tokenizer 重排了特殊 token，导致原始 SentencePiece 的 ID 需要偏移才能与 ONNX 模型对齐 |
| `eos_on_input` | boolean | `false` | 编码器输入末尾是否自动追加 EOS token，与 HuggingFace tokenizer 行为一致 |
| `decoder_start_token` | string | `null` | 解码器起始 token，设为 `"eos"` 表示使用 EOS token |
| `added_tokens` | map | `{}` | 语言代码等附加 token 的 ID 映射表，格式 `名称: ID`。provider 通过此映射查找语言代码 ID |

> **注意**：大多数模型无需 `tokenizer` 配置（默认无偏移）。仅当 HuggingFace tokenizer 对特殊 token 进行了重排（如 NLLB、部分 M2M-100 导出）时，才需要声明 `id_offset`。普通 SentencePiece 模型（如 Opus-MT）即使使用 `source.spm` + `vocab.json` 组合，也无需此配置。



#### 下载镜像优先级

镜像源优先级由配置文件 `application.yml` 的 `models.download.priority` 列表决定：

```yaml
models:
  download:
    priority:
      - modelscope      # 第一优先
      - hf-mirror       # 第二优先
      - github          # 第三优先
      - huggingface     # 第四优先（兜底）
```

- CLI 参数 `--mirror cn` 映射为 `priority: [modelscope, hf-mirror, gitee]`
- CLI 参数 `--mirror default` 映射为默认列表
- 每个模型文件的 `sources` 中只包含该文件实际可用的镜像
- `MirrorResolver` 按 `priority` 顺序为每个文件选择第一个有对应 URL 的镜像
- 优先选择国内镜像时可有效提升下载速度
- 支持并行、断点续传能力
- 多源自动切换下载能力
- 进度回调



### 1. 模型格式说明

votex 涉及以下模型格式：

| 格式 | 扩展名 | 说明 | 使用场景 |
|------|--------|------|---------|
| ONNX | `.onnx` | 开放神经网络交换格式，跨平台、跨框架推理 | TTS/ASR/OCR 推理 |
| PyTorch | `.pth` / `.pt` | PyTorch 原生序列化格式 | IndexTTS2 原始权重 |
| Safetensors | `.safetensors` | HuggingFace 安全张量格式，加载快、防恶意 | IndexTTS2 子模型 |
| NumPy npz | `.bin` | numpy 风格向量文件（非标准 bin） | Kokoro 音色嵌入 |

> **格式选择原则**：优先使用 ONNX（跨平台推理性能好，所有推理引擎均支持），PyTorch 格式仅作为原始权重保留。sherpa-onnx 加载的 Whisper/SenseVoice 模型底层也是 ONNX 格式。

##### 3.3.1 ONNX 版（VoiceDesign-1.7B-ONNX / ort 推理）

除 Candle 推理外，votex 也支持基于 **ONNX Runtime (ort)** 的 Qwen3-TTS 推理，使用 [Qwen3-TTS-VoiceDesign-ONNX](https://huggingface.co/colibriai/Qwen3-TTS-VoiceDesign-ONNX) 系列模型。

**文件结构：**

```
models/tts/qwen3-tts-1.7b/
├── qwen3-tts-1.7b.yaml              # 模型注册表（model_registry）
├── talker_prefill.onnx               # (1.26 GB) Talker 编码器（Prefill）
├── talker_prefill.onnx.data          # (3.73 GB) int4 量化权重
├── talker_decode.onnx                # (256 KB) Talker 解码器（Decode）
├── talker_decode.onnx.data           # (3.73 GB) int4 量化权重
├── code_predictor.onnx               # (23 KB) 码本预测器
├── code_predictor.onnx.data          # (0.31 GB) int4 量化权重
├── vocoder.onnx                      # (6.7 MB) CosyVoice3 声码器
├── vocoder.onnx.data                 # (0.42 GB) int4 量化权重
├── text_embedding.npy                # (52 MB) 词嵌入矩阵 [text_dim, 2048]
└── codec_embeddings.npz              # 码本嵌入（16组声学码本，每组 [8192, 2048]）
```

**注册表变体（qwen3-tts-1.7b 系列，每个变体一个 registry YAML）：**

| 变体 | 量化 | ONNX 布局 | 推荐 EP | 推理优化 |
|------|------|-----------|---------|---------|
| `direct-int4` | int4 | direct | CPU（DML 不兼容 MatMulNBits） | 体积最小 |
| `direct-int8` | int8 | direct | CPU / DML | 体积均衡 |
| `direct-fp16` | fp16 | direct | DML 优先 | GPU 推理 |
| `direct` | fp32 | direct | DML 优先 | 最高精度 |
| `wavekat` | fp32 | wavekat | DML 优先 | 原版 ONNX 导出 |

> **int4 + DirectML 不兼容**：int4 量化模型使用 `MatMulNBits` 算子，DirectML EP 不支持该算子。int4 变体会自动降级到 CPU EP。其他量化（int8/fp16/fp32）可正常使用 DirectML。
>
> **EP fallback 链**：`ep_priority: ["dml", "cpu"]` → DML 初始化失败自动降 CPU。

**四阶段推理流水线：**

```
文本 → Tokenizer → Embedding
  → ① Talker Prefill（编码完整序列 → logits + KV cache）
  → ② Talker Decode（自回归 × N 帧 → 码本流）
  → ③ Code Predictor（每帧 16 个码本组）
  → ④ Vocoder（码本序列 → 24kHz 波形）
```

Talker 解码器自回归运行（默认最多 4096 帧），每帧预测 16 个码本组。生成结束由 EOS token 控制（`codec_eos=3071`）。

**模型参数（VoiceDesign-1.7B）：**

| 参数 | Talker Prefill/Decode | Code Predictor | Vocoder |
|------|-----------------------|----------------|---------|
| hidden_size | 2048 | 2048 | — |
| num_hidden_layers | 28 | 5 | — |
| num_attention_heads | 16 | 16 | — |
| num_kv_heads | 4 | 4 | — |
| head_dim | 128 | 128 | — |
| intermediate_size | 7680 | 7680 | — |
| vocab_size | 3072 | 8192 | — |
| 输出采样率 | — | — | 24000 Hz |

**0.6B ONNX 模型差异**（基于 elbruno/Kokoro-Qwen3-TTS-0.6B）：
- `talker.hidden_size=1024`, `vocab_size=3072`, `num_hidden_layers=28`
- `code_predictor.onnx` 体积 420 MB（内部权重直接嵌入，1.7B 版仅 23 KB + 外挂 .data 文件）
- `cp_num_layers=5`, `cp_hidden_size=1024`

CTranslate2 是 OpenNMT 团队开发的 Transformer 专用推理引擎，支持 weights quantization、layers fusion、batch reordering 等优化技术，相比 ONNX Runtime 可实现 **2-4 倍加速**，内存占用降低 **50% 以上**。

**支持的模型格式转换：**

| 模型 | CTranslate2 格式 | int8 量化大小 | 速度提升 |
|------|-----------------|--------------|---------|
| OPUS-MT | ✅ 官方直接支持 | ~180MB | 2-3x |
| NLLB-200 distilled 600M | ✅ 支持 | ~1.2GB | 2-4x |
| M2M-100 418M | ✅ 支持 | ~750MB | 2-4x |
| M2M-100 1.2B | ✅ 支持 | ~2.5GB | 2-3x |
| Qwen-MT | ✅ 支持 | ~800MB | 2-3x |

**文件结构（以 OPUS-MT CTranslate2 为例）：**

```
models/translation/opus-mt-zh-en-ct2/
├── model.bin              # CTranslate2 量化模型文件
├── shared_vocabulary.json # 共享词汇表
├── source.spm             # 源语言 SentencePiece 分词器
└── target.spm             # 目标语言 SentencePiece 分词器
```

**集成说明：**

CTranslate2 提供 C++ API，Rust 可通过 FFI 绑定调用。集成方式：

1. 使用 `ct2-transformers-converter` 将 HuggingFace 模型转换为 CTranslate2 格式
2. 通过 `libloading` 在运行时动态加载 CTranslate2 动态库
3. 复用现有的 SentencePiece 分词器代码

```bash
# 转换 OPUS-MT 到 CTranslate2 格式（示例）
ct2-transformers-converter \
  --model Helsinki-NLP/opus-mt-zh-en \
  --output_dir opus-mt-zh-en-ct2 \
  --quantization int8
```

**集成状态：** ✅ FFI 骨架已创建（`CTranslate2Provider`），运行时动态加载 CTranslate2 动态库。需要系统安装 CTranslate2 C++ 库才能完整运行。

> CTranslate2 支持 encoder-decoder 架构（Marian、M2M-100、NLLB、BART、T5）和 decoder-only 架构（Llama、Mistral、GPT 等），是项目中长期最优的推理加速方案。

#### LLaMA / Mistral 通用 LLM 翻译

通用大语言模型（如 LLaMA、Mistral、Qwen 等）也可用于翻译任务，通过 prompt 指令实现翻译。这种方式灵活但质量和效率不如专用 MT 模型。

**适用场景：**

- 翻译 + 其他 NLP 任务（摘要、改写）的复合流水线
- 低资源语言对，专用 MT 模型覆盖不足时
- 需要结合上下文的长文档翻译

**不适用场景：**

- 纯批量翻译任务（效率低于专用 MT 模型 5-10 倍）
- 对延迟敏感的场景（首 token 延迟高）
- 低配 CPU 设备（7B+ 模型需要较大内存）

> votex 不将通用 LLM 作为首选翻译方案。除非用户已下载 LLM 用于其他功能，否则推荐使用专用 MT 模型。

  - 自动计算 SHA256 哈希

- GUI 模式下弹出确认对话框

#### 5.4 校验文件更新

- `checksums.json` 随程序内置（硬编码默认值）
- 模型更新时，新版本的哈希值通过下载元数据获取
- 用户也可手动更新 `checksums.json`



### 6. 模型下载策略

#### 6.1 下载源优先级

根据配置的镜像源（`models.mirror`）决定下载源尝试顺序：

| 镜像设置 | 下载源尝试顺序 | 说明 |
|---------|--------------|------|
| `default` | GitHub Releases → HuggingFace → hf-mirror → ModelScope | 优先官方源 |
| `cn` | ModelScope → hf-mirror → GitHub Releases → HuggingFace | 优先国内镜像 |

- 国内镜像说明：
  - **hf-mirror**：HuggingFace 镜像站（`hf-mirror.com`），覆盖全量 HuggingFace 模型
  - **ModelScope**：阿里云魔搭社区（`modelscope.cn`），国内访问稳定，需确认模型是否已上架
- 不使用网盘镜像（百度网盘、夸克网盘等），原因：无法程序化检测文件安全性和完整性，不支持断点续传

#### 6.2 下载流程

1. 用户选择要下载的模型
2. 程序根据镜像设置确定下载源优先级，按顺序尝试
3. 当前源连接失败（超时/网络错误）时，自动切换到下一个源
4. 下载到临时目录 `models/.tmp/{模型名}/`
5. 下载完成后校验 SHA256
6. 校验通过后移动到正式目录
7. 清理临时目录

#### 6.3 断点续传

- 下载过程中记录已下载字节数到 `models/.tmp/{模型名}/.progress`
- 中断后重新下载时，从已下载位置继续
- 临时文件损坏时自动重新下载
- 切换下载源时，若文件大小不一致则从头重新下载

#### 6.4 下载失败处理

- 当前源失败后自动尝试下一个源
- 所有源均失败时提示用户检查网络或手动下载
- 提供所有可用下载链接（可在浏览器中打开手动下载）
- 手动下载后通过 `votex model import` 导入
