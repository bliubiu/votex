# 29-本地服务化与能力自描述

## 概述

本节记录 P0 实施两项：**本地 HTTP 服务化（`votex serve`）** 与 **引擎/模型能力自描述**。两者复用现有业务逻辑（`votex-app::use_case`），遵循「最小改动、目标驱动、不动领域层核心逻辑」原则，严格符合 votex 的单二进制、离线优先、安全（内容零上传）设计。

## 1. 能力自描述（Engine/Model Capability Self-Description）

### 设计目标

为 CLI / API / Agent 提供**结构化、程序化发现**能力，消除「靠猜测可用引擎 / 音色 / 模型是否就绪」的问题。输出统一的能力元数据（分类、本地或在线、采样率、方言、零样本克隆、模型可用性等）。

### 能力报告结构

`CapabilityReport`（可直接 JSON 序列化）字段：

```text
{
  "version": "<crate version>",
  "models": [ { "id","name","kind","engine","engine_display_name","available","status" } ],
  "engines": [ { "engine","display_name","category","location","local","streaming","zero_shot_clone","sample_rate","dialects","notes" } ],
  "voices": [VoiceMeta...],
  "clone_voices": [ { "name","duration_ms","denoised","sample_rate","has_transcript" } ]
}
```

- **`engines.category`**：使用 `ProviderCapability::code()`（`tts/asr/ocr/llm/translation/video/runtime`），机器友好、避免中英文混杂。
- **`local`/`location`**：显式区分本地 ONNX 推理与在线 API（在线引擎含 Azure/Aliyun/DeepSeek/OpenAI/Gemini/Qwen 系列等）。
- **`sample_rate`/`dialects`**：provider 侧以运行期常量覆盖静态画像（`Kokoro/IndexTTS25/CosyVoice/Qwen3TTS`、`Whisper/SenseVoice/...` 均有确切值）。
- **`voices`**：来自 `platform::tts::list_engine_voices`（磁盘扫描），不加载模型，符合角色扫描与能力发现的「零加载」约定。

### CLI 用法

```bash
# 人类可读表格（原有行为不变）
votex model list

# 结构化能力报告（JSON，供脚本 / Agent 使用）
votex model list --json
```

> `model list --json` 输出**完整能力报告**（models + engines + voices + clone_voices），这是对「引擎/模型能力自描述」最直接的程序化发现入口。

## 2. 本地服务化（`votex serve`）

### 设计目标

提供轻量、本地、离线优先的 HTTP 服务：OpenAI 兼容的 TTS/ASR 能力、能力发现端点，以及 MCP（Model Context Protocol）JSON-RPC，全部复用现有 `votex-app` 用例，不新增业务逻辑。

### 技术选型

- **HTTP 服务器**：[`tiny_http`](https://crates.io/crates/tiny_http)（阻塞式、线程池）。未引入异步运行时，契合「单二进制分发、体积优先」约束。
- **线程模型**：按 `--workers`（默认 4）启动工作线程，每线程循环 `server.recv()` 处理请求。单个请求失败不终止工作线程。
- **鉴权**：可选 `--api-key`；设置后 `/v1` 与 `/mcp` 端点均需 `Authorization: Bearer <key>`。`/health` 永远放行以便探活。
- **CORS**：默认返回 `Access-Control-Allow-Origin: *`。
- **临时文件**：自实现轻量临时路径生成，音频/字幕临时文件使用后主动删除。

### API 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/health` | 存活探测，返回 `{"status":"ok","name":"votex","version":"..."}`，无需鉴权。 |
| `GET` | `/v1/capabilities` | 完整能力报告（JSON），等价于 `votex model list --json`。 |
| `GET` | `/v1/models` | OpenAI 兼容模型列表，筛选 `category == "tts" || category == "asr"`。 |
| `POST` | `/v1/audio/speech` | OpenAI 兼容语音合成，返回原始音频字节。复用 `TtsUseCase::synthesize`，本地推理。 |
| `POST` | `/v1/audio/transcriptions` | 语音识别（raw audio body + query params），返回 `{"text": "...","subtitles": [...]}`。复用 `AsrUseCase::recognize`。 |
| `POST` | `/mcp` | MCP JSON-RPC 2.0，支持 `initialize/ping/notifications/initialized/tools/list/tools/call`。 |

### MCP 工具

| 工具名 | 功能 | 说明 |
|---|---|---|
| `list_engines` | 列出引擎能力 | 返回 `report.engines` 的 pretty JSON。 |
| `list_models` | 列出模型清单 | 返回 `report.models` 的 pretty JSON。 |
| `tts_synthesize` | 文本转语音 | 写入音频文件并返回路径（支持 wav/mp3/m4a/flac）。 |
| `asr_transcribe` | 音频转文字 | 返回识别文本与字幕条目（txt/srt/lrc）。 |

### CLI 用法

```bash
# 启动本地服务（默认 127.0.0.1:3900，4 工作线程）
votex serve

# 指定地址/端口与 API Key
votex serve --host 127.0.0.1 --port 8080 --api-key secret --workers 2

# 健康检查
curl http://127.0.0.1:3900/health

# 能力发现
curl http://127.0.0.1:3900/v1/capabilities | jq .

# TTS（OpenAI 兼容）
curl -X POST http://127.0.0.1:3900/v1/audio/speech \
  -H "Content-Type: application/json" \
  -d '{"input":"你好，声阅","model":"kokoro","voice":"zf_001","response_format":"wav"}' \
  -o out.wav

# ASR（原始音频 body + 查询参数）
curl -X POST "http://127.0.0.1:3900/v1/audio/transcriptions?model=whisper-base&language=zh&format=srt" \
  -H "Content-Type: audio/wav" \
  --data-binary @audio.wav
```

> 默认仅监听 `127.0.0.1`（本机回环）。如需局域网访问，请显式指定 `--host 0.0.0.0` 并配合 API Key。

### 设计约束与取舍

- **零新业务逻辑**：全部复用 `votex-app::use_case`，服务层纯协议适配。
- **最小依赖**：选用 `tiny_http`，不引入 async 栈。
- **MCP 简化形态**：`POST /mcp` 覆盖 `initialize/tools/list/tools/call`，满足批一需求。
- **ASR 接口简化**：raw audio body + query params（非标准 multipart），已在文档明确。
- **鉴权粒度**：仅 Bearer Token，满足本地服务最小安全需求。

## 3. 兼容性与影响

- **向后兼容**：`votex model list` 行为不变，仅新增 `--json` 分支。
- **CLI 测试**：新增 `cli_model_list_json`、`cli_serve_默认参数`、`cli_serve_显式参数`，均通过。
- **单元测试**：domain 能力测试 8 项、app 能力报告测试 3 项、server 处理器辅助测试 3 项，全绿。
- **分层守恒**：表现层不直接依赖 infra，仍通过 `votex-app` 用例与平台门面访问资源。

## 4. 后续建议（P1/P2）

- 为 `votex serve` 补充优雅关闭与请求日志轮转。
- 补充 MCP 工具错误的结构化错误码映射（将领域错误映射到 `isError: true` 的工具结果）。
- 能力报告按需缓存（减少高频轮询开销）。
- 对齐 OpenAI `/v1/audio/transcriptions` 标准 multipart（可选增强）。

## 结论

本次实施严格遵循 votex 架构与约束，按最小改动完成 P0 两项。能力自描述为 Agent/脚本提供了统一的程序化发现入口，`votex serve` 则以轻量 HTTP + MCP 的形态将现有本地能力服务化，两者均复用同一套领域用例，确保 CLI/GUI/API 三端能力对等。
