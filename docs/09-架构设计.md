## 架构设计

基于 DDD 分层架构，定义 votex 的模块结构、依赖关系、Provider 抽象和关键技术决策。



### 1. 分层架构总览

```
┌──────────────────────────────────────────────────────────┐
│                      表现层 Presentation                  │
│  ┌────────────────────┐  ┌────────────────────────────┐  │
│  │    CLI (clap)       │  │    GUI (egui/eframe)       │  │
│  └────────┬───────────┘  └────────────┬───────────────┘  │
├───────────┼───────────────────────────┼──────────────────┤
│           │       应用层 Application   │                  │
│  ┌────────┴───────────────────────────┴───────────────┐  │
│  │              用例编排（Use Cases）                    │  │
│  │  TtsUseCase / AsrUseCase / OcrUseCase / ModelUseCase /           │  │
│  │  PipelineUseCase / ConfigUseCase / TaskUseCase      │  │
│  └────────────────────────┬───────────────────────────┘  │
├───────────────────────────┼──────────────────────────────┤
│                           │       领域层 Domain           │
│  ┌────────────────────────┴───────────────────────────┐  │
│  │  实体 / 值对象 / 领域服务 / 仓储接口（trait）         │  │
│  │  Model / TtsTask / AsrTask / OcrTask / Pipeline / AppConfig  │  │
│  │  TtsProvider(trait) / AsrProvider(trait) / OcrProvider(trait)│  │
│  └────────────────────────┬───────────────────────────┘  │
├───────────────────────────┼──────────────────────────────┤
│                           │     基础设施层 Infrastructure  │
│  ┌────────────────────────┴───────────────────────────┐  │
│  │  Provider 实现 / 仓储实现 / 文件 I/O / 外部库封装     │  │
│  │  KokoroProvider / IndexTts2Provider /               │  │
│  │  WhisperProvider / PaddleOcrProvider /              │  │
│  │  OnnxRuntime / GgmlEngine / FfmpegBridge            │  │
│  └────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
```

**依赖规则**：上层依赖下层，下层不依赖上层。领域层不依赖任何外部库，仅定义 trait 接口。



### 2. Crate 结构

采用 Rust workspace 多 crate 结构，实现分层隔离：

```
votex/
├── Cargo.toml                  # workspace 根
├── crates/
│   ├── votex-domain/           # 领域层：实体、值对象、领域服务、trait
│   ├── votex-app/              # 应用层：用例编排，依赖 votex-domain
│   ├── votex-infra/            # 基础设施层：Provider 实现、仓储实现
│   ├── votex-cli/              # 表现层：CLI 入口
│   └── votex-gui/              # 表现层：GUI 入口
├── models/                     # 模型文件目录（运行时）
├── docs/                       # 项目文档
└── src/
    └── main.rs                 # 二进制入口，根据参数启动 CLI 或 GUI
```

#### 2.1 Crate 依赖关系

```
votex-cli ──→ votex-app ──→ votex-domain ←── votex-infra
votex-gui ──→ votex-app ──→ votex-domain ←── votex-infra
                                  ↑
                            (trait 定义在此)
```

| Crate | 依赖 | 说明 |
|-------|------|------|
| `votex-domain` | 无外部依赖 | 纯领域逻辑，定义 trait 和实体 |
| `votex-infra` | `votex-domain` + 外部库 | 实现领域层定义的 trait（ONNX / SQLite / 网络 / 文件） |
| `votex-app` | `votex-domain` + `votex-infra` | 用例编排 + **装配根**（`bootstrap::AppContext`）+ **基础设施门面**（`platform`） |
| `votex-cli` | `votex-app` + `clap` | CLI 表现层，只做参数解析与输出格式化 |
| `votex-gui` | `votex-app` + `egui` | GUI 表现层，只做交互与渲染 |
| `votex`（bin） | `votex-cli` + `votex-gui` | 主入口，仅做「CLI 模式 / GUI 模式」分发 |

**分层红线**：`votex-cli` / `votex-gui` 中**不允许出现** `votex_infra::` 或 `rusqlite`。
换基础设施实现时只改 `votex-app::platform` 内部，表现层零改动。

#### 2.2 依赖注入（AppContext 装配根）

装配统一收敛到 `votex-app::bootstrap::AppContext`，CLI 与 GUI 共用同一份流程：

```rust
// crates/votex-cli/src/lib.rs
let ctx = AppContext::bootstrap(
    BootstrapOptions::new("application.yml")
        .with_models_dir(Some(cli.models_dir.into()))
        .with_log_level(cli.verbose.then(|| "debug".into())),
)?;

// 仓储以 domain trait object 持有，表现层不感知 SQLite
if let Some(repo) = ctx.ocr_repo() {
    OcrUseCase::new().with_repo(repo.clone());
}

// GUI 模式：把装配结果交给 GUI，不重复初始化
if cli.gui {
    return Ok(RunMode::Gui(Box::new(ctx)));
}
```

`AppContext::bootstrap` 内部顺序**不可调整**：

1. **ONNX Runtime 动态库定位** —— 必须最先。`ort` 首次调用会按默认名加载动态库并缓存失败结果，
   缓存后即使再设 `ORT_DYLIB_PATH` 也无效。
2. **加载 `application.yml`** —— 先于日志初始化（日志级别来自配置）。
   文件不存在 → 用默认值；解析失败 → 写 stderr 提示但**不阻断启动**。
3. **日志初始化** → 4. **执行提供器与推理资源限制** → 5. **资源治理阈值**
6. **模型目录解析**（`WorkspacePaths`，不依赖 CWD）
7. **下发下载配置**（超时 / 断点续传）→ 8. **翻译运行时**（会话池 + 缓存）
9. **打开 SQLite**（WAL + `foreign_keys` + 版本化迁移）并构造各仓储 trait object

数据库不可用属于**可降级故障**：记录告警后所有仓储为 `None`，
依赖持久化的功能自动关闭，其余功能照常工作。

#### 3.2 Provider 抽象

**共享引用契约（P2-17 起）**

所有 provider trait 的生命周期方法统一收 `&self`：

- `load` / `unload` 与 `recognize` / `synthesize` 同为**共享引用**，
  因为「加载模型」改的是引擎**内部状态**（ONNX Session、分词器、词表），
  不是 provider 对象自身的字段布局。`&mut self` 会迫使上层为「查一下是否已加载」
  这类只读意图也持独占锁。
- 内部可变状态统一由 `votex_infra::shared::EngineState<T>`（封装 `Mutex<Option<T>>`）管理。
  引擎适配器的裸字段（`tokenizer` / `tokens` / `dict` / `variant` …）已全部改为
  `EngineState<T>`，不再手写 `Mutex<Option<Session>>`。
- `EngineState::get()` **一律返回 `MutexGuard`**，调用方必须在 `with()` 闭包内完成
  分词 / 查表 / 解码，只带出 owned 数据。
  跨守卫借用引用会触发 `cannot return value referencing function parameter`，
  这是有意为之的约束 —— 不提供 `unsafe` 快捷路径。

由此上层用例（`TtsUseCase` / `AsrUseCase` / `OcrUseCase`）全部方法都是 `&self`，
用例对象可跨线程共享。

**TtsProvider trait**

```rust
pub trait TtsProvider: Send + Sync {
    /// 返回引擎类型
    fn engine_kind(&self) -> EngineKind;

    /// 加载模型到内存
    fn load(&self, model: &Model) -> Result<()>;

    /// 释放模型资源
    fn unload(&self) -> Result<()>;

    /// 合成单段语音
    fn synthesize(
        &self,
        text: &str,
        voice: &VoiceId,
        params: &TtsParams,
    ) -> Result<AudioData>;

    /// 列出可用音色
    fn list_voices(&self) -> Vec<VoiceId>;

    /// 输出采样率
    fn sample_rate(&self) -> u32;

    /// 是否已加载
    fn is_loaded(&self) -> bool;
}
```

**AsrProvider trait**

```rust
pub trait AsrProvider: Send + Sync {
    /// 返回引擎类型

    /// 加载模型到内存

    /// 释放模型资源
```

**扩展性**：后续版本新增引擎或在线 API 时，只需实现对应 trait 并注册到 Provider 容器中，无需修改领域层和应用层代码。

**OcrProvider trait**

```rust
pub trait OcrProvider: Send + Sync {
    /// 返回引擎类型
    fn engine_kind(&self) -> EngineKind;

    /// 加载模型到内存
    fn load(&self, model: &Model) -> Result<(), OcrError>;

    /// 释放模型资源
    fn unload(&self) -> Result<(), OcrError>;

    /// 识别单张图片
    fn recognize(&self, image_path: &Path, params: &OcrParams) -> Result<OcrResult, OcrError>;

    /// 识别单张图片（带取消与进度回调）
    ///
    /// 默认实现忽略取消与进度，直接委托 `recognize`；引擎可覆写。
    /// **覆写时必须用完全限定名**（如 `PaddleOcrEngine::recognize_with_cancel(self, ..)`），
    /// 写成 `self.recognize_with_cancel(..)` 会解析回 trait 方法本身 → 无限递归栈溢出。
    fn recognize_with_cancel(
        &self,
        image_path: &Path,
        params: &OcrParams,
        cancel_token: &CancellationToken,
        on_progress: ProgressCallback,
    ) -> Result<OcrResult, OcrError>;

    /// 是否已加载
    fn is_loaded(&self) -> bool;
}
```

**TranslationProvider trait**

只有 `name` 与 `translate` 是必须实现的，其余均提供默认实现，
让在线 API / 词典类引擎无需写加载逻辑。

```rust
pub trait TranslationProvider: Send + Sync {
    /// 提供者名称（唯一标识，如 "opus-mt"）
    fn name(&self) -> &str;

    /// 翻译文本
    fn translate(&self, text: &str, direction: TranslationDirection)
        -> Result<String, TranslationError>;

    // ---- 生命周期（默认实现：在线/词典引擎无需加载）----
    fn load(&self, _model_dir: &Path) -> Result<(), TranslationError> { Ok(()) }
    fn unload(&self) {}
    fn is_loaded(&self) -> bool { true }

    /// 批量翻译（默认逐条委托 `translate`，引擎可覆写为真批处理提效）
    fn translate_batch(&self, …) -> …;

    /// 流式翻译（默认一次性返回，引擎可覆写为逐块回调）
    fn translate_stream(&self, …) -> …;

    /// 是否支持术语表注入
    /// 默认 `false`：纯 Encoder-Decoder 离线模型无法注入术语表，
    /// 此时由上层流水线改用「占位符替换」保证术语一致。
    fn supports_glossary_prompt(&self) -> bool { false }
}
```

#### 4.2 进程级用例单例

三个重量级用例持有 ONNX Session 与分词器等 GB 级资源，
若每个任务各自 `new()` 会重复加载权重。

`services/shared_cases.rs` 提供 `OnceLock<Arc<UseCase>>` 单例：

```rust
pub fn shared_tts() -> Arc<TtsUseCase>
pub fn shared_asr() -> Arc<AsrUseCase>
pub fn shared_ocr() -> Arc<OcrUseCase>
```

GUI 的 `task_runner.rs`、CLI 命令、批处理与流水线用例统一走这三个入口。
这依赖 3.2 节的 `&self` 契约 —— 用例方法全部共享借用，才能放进 `Arc` 跨线程传递。

#### 4.3 用例编排示例

**TtsUseCase** 编排流程：

```
1. 验证输入（文件存在、参数合法）
2. 加载 TTS 模型（若未加载）
3. 文本预处理 + 分段
4. 逐段合成（调用 TtsProvider）
5. 音频拼接（调用 AudioConcatenator）
6. 导出文件
7. 渐进式质量提示（若开启）
8. 更新任务状态
```

**PipelineUseCase** 编排流程：

```
1. 根据 PipelineKind 构建阶段列表
2. 逐阶段执行，阶段间传递中间产物
3. 任一阶段失败 → 暂停，等待用户操作
4. 全部完成 → 渐进式质量提示
```

#### 5.3 下载器设计

**多源下载策略**

```
MirrorResolver
  ├── resolve(entry, priority) → Vec<DownloadFile>  // 按优先级返回 URL 列表
  │
Downloader
  ├── download(urls: Vec<Url>, dest: &Path) → Result<()>
  │   ├── 尝试第一个 URL
  │   ├── 失败 → 尝试下一个 URL
  │   ├── 支持 HTTP Range 断点续传
  │   └── 全部失败 → 返回错误
  │
SqliteDownloadRepository  ← 下载进度回调写入
  ├── 初始状态 Pending
  ├── 开始下载 → Downloading（记录已下载字节数）
  ├── 进度更新 → update_progress()（每 1MB 或完成时）
  ├── 完成 → Completed
  └── 启动时 find_incomplete() → 恢复未完成的下载
```

#### 6.3 异步任务执行

TTS/ASR 推理为 CPU 密集型，在独立线程中执行：

```
┌─────────────┐     命令/请求      ┌──────────────┐
│  GUI/CLI     │ ──────────────────→ │  任务线程      │
│  (主线程)    │ ←────────────────── │  (推理执行)    │
│              │     进度/结果       │              │
└─────────────┘                     └──────────────┘
```

- 主线程负责 UI 渲染和用户交互
- 任务线程执行推理，通过 channel 发送进度和结果
- 同一时刻仅 1 个 TTS 任务 + 1 个 ASR 任务执行（避免内存峰值叠加）



### 7. 错误处理策略

#### 7.1 错误类型层次

```rust
// 领域层错误
enum DomainError {
    Model(ModelError),
    Tts(TtsError),
    Asr(AsrError),
    Ocr(OcrError),
    Pipeline(PipelineError),
    Config(ConfigError),
}

// 各子错误类型映射到错误码
impl DomainError {
    fn error_code(&self) -> &str {
        match self {
            DomainError::Model(e) => e.code(),    // VM001 ~ VM010
            DomainError::Tts(e) => e.code(),      // VT001 ~ VT011
            DomainError::Asr(e) => e.code(),      // VA001 ~ VA007
            DomainError::Ocr(e) => e.code(),      // VO001 ~ VO007
            DomainError::Config(e) => e.code(),   // VC001 ~ VC004
            DomainError::Pipeline(e) => e.code(), // VP001 ~ VP005
        }
    }
}
```

#### 7.2 错误传播

```
基础设施层 → Result<T, InfraError>
    ↓ 转换
领域层 → Result<T, DomainError>
    ↓ 转换
应用层 → Result<T, AppError>（附带用户提示文案）
    ↓ 转换
表现层 → CLI: stderr 输出 / GUI: 提示对话框
```

- 领域层和基础设施层使用 `thiserror` 定义错误类型
- 应用层将技术错误转换为用户友好的中文提示
- 表现层根据错误类型选择展示方式（Toast/Dialog/Inline）



### 8. 关键技术决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 异步运行时 | 不使用 async runtime | 推理为 CPU 密集型，使用线程池而非 async；下载使用独立线程 + 阻塞 HTTP |
| 线程管理 | `std::thread` + `crossbeam-channel` | 简单可靠，避免引入 tokio 的复杂性 |
| GUI 框架 | egui + eframe | 即时模式，适合工具类应用，单二进制分发友好 |
| ONNX 推理 | ort（ONNX Runtime Rust 绑定） | 成熟稳定，CPU 推理性能好 |
| ASR 推理（Whisper/SenseVoice） | sherpa-onnx | 统一 ASR 推理框架，ONNX 格式支持，多引擎封装 |
| ASR 推理（Paraformer） | ort（ONNX Runtime Rust 绑定） | 直接 ONNX Runtime 调用，低延迟 |
| ASR 推理（Qwen3-ASR/FireRedASR） | sherpa-onnx Rust 绑定 | 官方预转换分图 ONNX，低延迟 |
| 音频处理 | ffmpeg-next | 功能全面，支持多格式编解码 |
| 配置格式 | YAML（serde_yaml） | 可读性好，适合手动编辑 |
| 持久化格式 | SQLite（rusqlite，bundled）+ JSON 序列化 | 任务/流水线数据支持跨会话恢复，JSON-in-column 模式避免 schema 迁移 |
| 错误处理 | thiserror + anyhow | 领域层用 thiserror 定义精确错误，应用层用 anyhow 简化 |
| 日志 | tracing + tracing-subscriber | 结构化日志，支持文件轮转 |
